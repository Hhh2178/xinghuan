## AICopy SD 视频契约与四种输入模式灰度

目标:
- 将 AICopy 传输协议与 SD 模型补充契约限制在显式 Provider 协议和模型开关内。
- 支持参考图、首帧、尾帧、首尾帧四种通用视频输入模式。
- 在不影响生产 `v0.5.22` 的前提下部署灰度 `v0.6.4`。

变更:
- 新增 AICopy 请求契约、结果路径和模型配置工具。
- 视频节点和 API 统一执行四种模式的数量约束与顺序语义。
- Worker 仅在 `provider.protocol=aicopy` 且模型显式开启契约时发送 SD 字段。
- 修正 external video、Worker queue 与画布节点渲染验证脚本。

验证:
- 离线适配器、API 输入验证、Provider task service、类型检查和单端口构建通过。
- 灰度 API/Worker active，公网与内网状态为 `v0.6.4 / gray`。
- Mock 上游、真实 Redis 队列和画布 `49/49` 节点渲染 smoke 通过。
- 已有成品 `content.mp4` 为 H.264、`1254x720`、30 fps、15 秒，无音频流。
- PostgreSQL 只读取证确认真实任务保存 `ratio=9:16`、`duration=15`、`modeType=text2video`、声音固定绑定和空 `fixedBody`。

影响:
- 第一阶段代码、配置、灰度与离线验收链路已建立。
- 成品时长符合要求，但比例与声音未被上游应用，不能标记媒体契约完全通过。

风险:
- Worker 当前不持久化脱敏后的最终上游请求快照，尚缺网络层字节级证据。
- 接口文档与 AICopy 实际执行契约可能存在差异。

下一步:
- 禁止继续直接调用昂贵 SD 模型进行试错。
- 通过插件源码、供应商任务日志或 Mock 上游继续无费用核对比例和声音字段。
- 进入后台全局布局、文字溢出、RH 应用与 RunningHub Key 池信息架构第二阶段整改。
