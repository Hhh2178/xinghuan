## RunningHub 多 Key 抢占缺口修复第一阶段止血

目标:
- 修复 RH Key 池存在余量但任务仍提前进入 `all_keys_busy` / 提前排队的问题。
- 把 worker 的 RH Key 抢占从“先选 Key、后占位”改为“按顺序逐把尝试占位”。
- 保持 API 侧 `preferredRhKeyId` 与 worker 侧 `assignedRhKeyId` 的现有对外字段不破坏。

根因:
- 旧实现先 `selectExecutableRunningHubKey()` 选出一把可用 Key。
- 随后才对这把 Key 做 Redis `incr` 占位。
- 如果这把 Key 在竞争中被别的任务抢先占满，当前任务会直接返回 busy，不会继续尝试下一把仍有余量的 Key。

变更:
- `apps/worker/src/worker.ts`
  - 保留 `selectExecutableRunningHubKey()` 作为只读选择语义
  - 新增 `acquireExecutableRunningHubKey()`，真正按候选顺序逐把执行占位
  - 当单把 Key 在 `incr` 后发现超限时，先 `decr` 回滚，再 `continue` 尝试下一把
  - 只有所有候选 Key 都失败后，才统一返回 `RunningHub 所有 Key 并发已满 (all_keys_busy)`
- 新增契约：
  - `scripts/verify-runninghub-key-acquire-fallback.mjs`

验证:
- `node scripts/verify-runninghub-key-acquire-fallback.mjs`
- `node scripts/verify-runninghub-dynamic-key-selection-contract.mjs`
- `node scripts/verify-runninghub-key-pool-contract.mjs`
- `npm run type-check -w @xinghuan/worker`

当前结论:
- worker 侧 RH Key 抢占已经不再是“占位失败立即 busy”。
- 现在会继续尝试后续 Key，直到全部失败才进入 `all_keys_busy`。

仍待后续验收:
- 我当前还没有独立完成真实 gray 多 Key 业务压测，不能单凭静态契约证明“轮转体验完全符合预期”。
- 我当前还没有独立证明 Redis 窗口在高并发长时间运行下不存在极端泄漏，这需要 gray 上真实业务观察。
