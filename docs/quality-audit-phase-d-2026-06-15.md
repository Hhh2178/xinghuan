# Phase D 完成后的新一轮整体检测报告（2026-06-15）

## 结论摘要

- 当前项目已经完成 `Phase A -> Phase D` 的关键收口，正式多用户风险从“结构性不可控”下降到了“仍需继续治理但已可分层管理”的状态。
- 本轮 `Phase D` 完成后，任务系统相比之前最大的变化是：
  - 取消语义不再伪装
  - 长轮询任务具备 heartbeat
  - 悬挂运行任务有 reaper 补偿
  - 后台任务查询不再默认全量返回
- 当前最值得继续推进的部分已经从“数据会不会被覆盖”转移到了“请求链路可观测性、系统观测面板、正式环境压测与多租户边界再验证”。

## 本轮验收范围

- 类型检查：
  - `@xinghuan/api`
  - `@xinghuan/worker`
  - `@xinghuan/admin`
  - `@xinghuan/web`
- 构建：
  - `npm run build:single-port`

  - `node scripts/verify-task-cancellation-phase-d.mjs`

  - `npm run verify:phase-d`

- 这一点也进一步证明：正式多用户稳定性判断必须以 PostgreSQL 运行态为主，而不是以本地文件模式为主。
- 额外复核脚本：
  - `npm run verify:multi-user-isolation`
  - `npm run verify:canvas-revision-conflict`

## 一、框架层分析

### 当前状态

- Monorepo 分层已经比较清晰：
  - `apps/web` 负责画布前端
  - `apps/admin` 负责后台
  - `apps/api` 负责 API 与仓储
  - `apps/worker` 负责异步任务执行
  - `packages/*` 承担共享类型、模型治理与 UI 基础
- 当前架构已经从“直接同步调用第三方生成”转到了“任务化 + 队列 + Worker”的正式形态。
- Phase A/B/C/D 连续推进后，核心基础能力已经具备：
  - owner 归属保护
  - revision 冲突保护
  - session 治理
  - CSRF 防护
  - 登录限流
  - 任务运行态与取消闭环

### 优点

- 前后端边界比早期版本清晰很多，后台、画布、任务系统已不是一团混合状态。
- Provider 扩展机制逐渐形成“协议层 + adapter 层 + 模型高级配置层”的结构，后续可继续标准化。
- Worker 分类队列与执行模式语义已经明确，有利于后面做更细粒度并发治理。

### 当前缺失

- 还缺少统一的请求级 trace 机制，`requestId` 尚未成为 API / Worker / 审计 / 前端错误展示的公共主键。
- file-mode 仍然保留，适合本地开发，但不适合作为正式多用户质量依据；后续需要更明确地把它界定为“开发态兼容层”。
- 当前仍有一些大文件前端资源包，说明前端交付物体积和按需拆分还有优化空间。
- 本地 `file-mode` 复核中还观察到“同一个 foreign canvas id 在另一个用户命名空间里形成影子副本”的现象；它不会直接改写他人数据，但说明 file-mode 语义与 PostgreSQL 正式仓储并不一致。

### 结论

- 框架层已经脱离“高危原型期”，进入“可演进正式系统”的阶段。
- 下一阶段重点不应再是继续堆业务功能，而应优先补全 `Phase E` 的链路化观测能力。

## 二、前端层分析

### 当前状态

- 画布前端和后台前端都已经有较稳定的独立入口。
- 后台任务面板已经从“全量数组前端本地过滤”切换为“服务端分页 + 服务端过滤”。
- 取消状态展示已经开始区分真实语义，不再把所有取消都包装成“上游已终止”。

### 优点

- 后台任务 UI 的数据流更健康，避免任务量变大后页面一次性吞下所有任务数据。
- 前端取消接口返回结构更明确，后续可以继续把取消结果、补偿状态、失败原因做成更清晰的运维视图。
- 管理后台与画布的职责比之前更清爽，后续扩展系统观测面板有空间。

### 当前问题

- Web 端打包体积仍偏大，尤其是画布主包和图标/大图资源，对首屏与弱网体验有压力。
- 前端错误展示虽然比之前更清晰，但对“提交失败、轮询失败、结果拉取失败、补偿回收失败”这几类任务错误的分层还不够统一。
- 任务页虽然完成了分页，但审计页、素材页、生成库这类高数据量页面后续仍应继续做同类治理，避免再次出现“局部先进、整体回退”的情况。

### 建议

- 在 `Phase E` 中把错误展示规范继续统一成：
  - 用户提示文案
  - 可读失败原因
  - 技术排查字段
- 对大资源做进一步按需加载与分包检查，尤其是画布主包和图标包。

## 三、后端层分析

### 当前状态

- API 层已经完成多轮关键收口：
  - owner 校验
  - revision 冲突
  - session 元数据与治理
  - CSRF 同源校验
  - 登录限流
  - 统一任务取消服务
- Worker 层已经不再只是“成功/失败二值执行器”，而是具备最基础的运行态观测与补偿。

### 优点

- 任务取消已经开始尊重上游真实能力，这是正式系统需要的语义严谨性。
- heartbeat 与 stale reaper 的引入，意味着系统开始能够识别“假运行中”任务。
- API 端对任务状态返回结构的补强，使前端和后台不再只能靠猜测任务真实状态。

### 当前问题

- 上游取消能力仍依赖 Provider/模型高级配置，尚未形成全平台统一的 provider cancel registry。
- 任务补偿当前还是基础版 reaper，属于“兜底回收”，不是完整的 reconciliation engine。
- API / Worker 日志还没有完全统一的 `requestId` 与结构化追踪字段，后续排障仍然需要人工拼接上下文。

### 建议

- `Phase E` 优先建立：
  - `requestId`
  - `taskId`
  - `userId`
  - `providerId`
  - `modelId`
  的统一日志透传。
- 对 Provider 能力继续分类：
  - 支持真实取消
  - 仅支持本地取消
  - 支持查询但不支持取消
  - 支持补拉最终结果

## 四、数据库层分析

### 当前状态

- PostgreSQL 已经成为正式运行主存储。
- 画布、资源、后台关键设置已经开始向实体级写入与 revision 保护收口。
- 本轮新增 `xh_tasks` 索引后，任务分页查询具备了更合理的数据库基础。

### 优点

- 数据库目标防呆已经落地，显著降低了“连错库导致看起来像数据清空”的风险。
- 任务表已经开始按运行态查询需求建立索引，而不是继续把数据库当 JSON 文件替代物。
- 多用户风险最大的 owner 接管与整表替换已经在前几轮被显著削弱。

### 当前问题

- 虽然高风险整表写入已连续收口很多，但整体仓储层仍需持续审查，避免旧路径残留。
- 审计、任务、素材、生成库的长期容量增长后，还需要进一步评估更多组合索引和归档策略。
- 本地 file-mode 与 PostgreSQL 行为差异较大，容易让开发验收与正式运行产生错觉。
- 本地 file-mode 的 `canvasId` 在跨用户写入时会形成“每用户各自持有同 id 文件”的影子状态，这对于开发调试可容忍，但不应被误判为正式多用户仓储设计。

### 建议

- 后续所有“正式质量结论”都必须以 PostgreSQL 模式验收为准。
- 为高频查询补基于真实筛选条件的索引，而不是一次性堆很多宽泛索引。
- 提前规划：
  - 任务归档
  - 审计归档
  - 生成库过期清理
  - 慢查询观察

## 五、作为正式多用户服务器项目，当前仍缺的东西

### P0-P1 级别

- 统一请求链路追踪：
  - 缺少完整 `requestId` 贯通
- 更完整的系统观测面板：
  - 队列积压
  - 失败趋势
  - reaper 命中
  - 冲突写入统计
- 正式环境下更稳定的批量验收基线：
  - 当前本地验收已可用，但正式多用户结论仍需更多灰度/生产真实样本

### P2 级别

- 更系统的前端分包与性能治理
- 更统一的 Provider 能力描述与自动测试矩阵
- 更明确的仓储层代码规范，避免新功能回退到整表写入思维

## 六、建议的下一步

   - 后台补系统观测面板

3. 补正式发布前的固定质量门槛

## 当前判断

- 现在的项目已经不再是“勉强能跑的单用户原型”，而是进入了“需要继续完善治理与观测能力的正式多用户系统”阶段。
- 如果后续继续严格按 `Phase` 推进，而不是回到零散热修，这个项目是可以继续稳定上线演进的。
