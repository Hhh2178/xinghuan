# RunningHub Key Pool And Node Progress Design

## 目标

本次设计用于收口 RunningHub 在无限画布 2.0 中的三类问题：

- 画布 RH 节点缺少与生成节点一致的阶段进度反馈，排队与运行状态不直观。
- 画布 RH 节点参数区暴露过多技术描述，普通用户难以理解，且后台填写的备注名没有稳定覆盖前台显示。
- 后台 RunningHub 工作台仍然只有单 Key 能力，无法承载多 Key 号池、单 Key 并发治理、自动切 Key 和总并发汇总。

同时，本轮还补充一条协作治理要求：

- 在当前仓库的命令检索、读文件、git 状态与脚本执行过程中，默认优先使用 RTK，以减少高频终端输出带来的 token 消耗。

## 本轮要解决的问题

### 1. RH 节点阶段反馈不足

当前 RH 节点可以提交和轮询任务，但用户看不到明确的阶段进度条。提交后即使任务已经进入队列或已经开始运行，节点顶部仍缺少统一的状态表达，造成用户误判为“没反应”或“不知道是否在排队”。

### 2. RH 参数区过于工程态

当前参数区存在大量类似：

- `来自 requestExample.nodeInfoList 的 284.image`
- `来自 requestExample.nodeInfoList 的 314.prompt`

这类描述对后台管理员校对输入槽来源有价值，但对画布使用者没有帮助，反而会放大技术噪音。

同时，后台在字段层已经允许维护更友好的备注或显示名，但前台节点并没有稳定采用“备注优先、字段名兜底”的显示策略。

### 3. RH 仍是单 Key 模式

当前 RunningHub Provider 主要依赖单一 `apiKey` 与平台级 `runninghub.concurrency`。这会带来三个限制：

- 无法把多个 RH Key 组成号池。
- 无法按 Key 单独配置最大并发。
- 无法在某个 Key 并发满时自动切换到其他 Key。

### 4. RH 总并发口径与资源真实情况脱节

当 RH 实际上已经有多个 Key 时，如果仍让管理员手工维护一个平台总并发数字，那么这个数字很容易与 Key 池真实可用能力脱节，最终造成“配置上看有余量，但运行中仍排队”的问题。

### 5. RTK 使用规则缺少仓库内显式约束

根级规则与本机技能已经要求优先使用 RTK，但当前无限画布 2.0 仓库自身的 `AGENTS.md` 还没有把这条规则内化为项目协作约定，导致执行层仍可能漂移。

## 设计原则

### 1. RH 节点对普通用户保持业务态，对管理员保留技术态

画布节点优先展示普通使用者真正需要的信息：

- 条目名称
- 参数名
- 参数值
- 阶段进度
- 结果或错误

字段来源、原始 nodeId、字段推导说明等技术信息继续保留在后台工作台，而不是默认堆在画布节点里。

### 2. RH 进度采用阶段型进度，不伪装成真实百分比

RunningHub 当前链路没有稳定的连续进度百分比，因此本轮只做阶段型进度：

- 已提交但未开始执行：`5%`
- 已开始运行：`45%`
- 成功：`100%`
- 失败：失败态

如果仍在平台队列中，维持 `5%` 并明确显示排队提示。

### 3. Key 池是 RH 专用调度能力，不污染通用 Provider 基础字段

RunningHub 的多 Key 管理、单 Key 并发和自动切 Key 是协议域内的专用能力，不应继续挤进通用单 `apiKey` 字段模型。应给 RH Provider 增加独立的 `rhKeyPool` 承载结构。

### 4. 总并发由启用中的 Key 自动汇总，不再手工维护

只要 RH Key 池存在，平台总并发就应该来自：

- `sum(enabled rhKey.maxConcurrency)`

后台可以展示这个值，但不再把它当作一个独立、可随意填写的主配置项。

### 5. 删除操作坚持单条删除

由于当前仓库与根协作规则都禁止批量删除，因此 RH Key 池只允许单 Key 明确删除，不提供批量删除动作。

### 6. RTK 作为默认终端执行偏好写入项目规则

RTK 不是一次性提醒，而是当前仓库的协作习惯。应把它明确写进 `AGENTS.md`，让后续实现、排障、验证与提交操作都遵守同一口径。

## 方案比较

### 方案 A：节点轻改 + 后台只加 Key 文本框

特点：

- 节点加进度条
- 后台把单个 `apiKey` 改成多行文本
- 不做真正的 Key 池调度

优点：

- 改动表面上最少

缺点：

- 后端无法知道每个 Key 的并发上限
- 无法精确判断“哪个 Key 满了”
- 只是把单 Key 输入框变成了多 Key 文本框，不能真正解决并发与排队问题

### 方案 B：节点状态、参数区和 RH Key 池一起收口

特点：

- 画布节点增加阶段进度条与排队提示
- 参数区默认隐藏技术描述，采用备注优先显示
- 后台新增 RH Key 池折叠卡片
- 后端与 Worker 补齐单 Key 分配和总并发汇总逻辑

优点：

- 体验、配置、调度三个层面一次打通
- 解决的问题与用户实际反馈一致
- 为后续 Key 健康状态、自动禁用和失败重试留下扩展位

缺点：

- 涉及 `apps/web`、`apps/admin`、`apps/api`、`apps/worker`

### 方案 C：先只做 Key 池，节点后续再改

优点：

- 后端能力优先落地

缺点：

- 用户前台感知改善滞后
- 节点仍然保留当前的噪音描述与状态不明确问题

### 结论

本轮采用 **方案 B**。

## 范围与非目标

### 范围内

- RH 工作台新增下侧折叠式 Key 池管理卡片
- Key 池支持新增、编辑、启停、单条删除
- 每个 Key 支持备注、密钥、最大并发
- RH 总并发改为 Key 池启用项自动汇总
- RH 任务提交按 Key 空余并发自动选择可用 Key
- RH 节点顶部增加阶段进度条
- RH 节点在排队时显示提示文案
- RH 节点参数区默认隐藏技术描述
- RH 字段显示名采用备注优先、字段名兜底
- `AGENTS.md` 增加 RTK 默认使用规则

### 非目标

- 不实现 Key 健康评分与自动熔断
- 不实现“某个 Key 报错后自动迁移重试到其他 Key”
- 不实现批量删除 Key
- 不实现 RH 官方真实百分比进度
- 不把画布上的视觉验收职责转移给 Agent

## 详细设计

### 一、后台 RunningHub Key 池管理

#### 1. 布局

在 RH 工作台右侧编辑区的下侧新增一个默认折叠的卡片：

- 标题：`RH Key 池管理`
- 默认状态：折叠
- 标题摘要：`{启用 Key 数} 个启用 / 总并发 {N}`

展开后展示：

- 顶部摘要区
- `新增 Key` 按钮
- 单 Key 列表

不采用左右并排拆分当前主编辑区，避免压缩 RH 条目编辑与分析区域的横向空间。

#### 2. 单 Key 结构

每个 Key 项包含：

- `id`
- `note`
- `apiKeyCipher`
- `apiKeyPreview`
- `maxConcurrency`
- `enabled`
- `createdAt`
- `updatedAt`

建议命名：

```ts
interface RunningHubKeyPoolItem {
  id: string;
  note: string;
  apiKeyCipher: string;
  apiKeyPreview: string;
  maxConcurrency: number;
  enabled: boolean;
  createdAt: number;
  updatedAt: number;
}
```

并在 RH Provider 记录中新增：

```ts
rhKeyPool?: RunningHubKeyPoolItem[];
```

#### 3. 单 Key UI 交互

列表默认只显示摘要：

- 备注
- 脱敏 Key 预览
- 最大并发
- 启用状态
- 当前占用数（若运行态已可读）

每一行支持：

- `编辑`
- `启用/停用`
- `删除`

点击编辑后，仅展开当前项的表单：

- 备注输入框
- API Key 输入框
- 最大并发输入框
- 启用开关
- 保存 / 取消

删除规则：

- 只允许单条删除
- 删除前要求明确确认
- 不提供“批量删除”或“清空 Key 池”

#### 4. 兼容旧单 Key 模式

迁移原则：

- 若 `rhKeyPool` 为空但旧 `provider.apiKey` 存在，则系统把它视为“兼容单 Key 模式”
- 首次进入并保存 RH Key 池后，后续 RH 运行优先读取 `rhKeyPool`
- 旧 `provider.apiKey` 保留兼容读取路径，但不再作为 RH 新配置的主入口

### 二、RH Key 分配、占用与排队

#### 1. 分配策略

本轮采用“稳定顺序扫描 + 只选择有空余并发的 Key”：

1. 过滤出 `enabled === true` 的 Key
2. 读取每个 Key 当前占用数
3. 按稳定顺序扫描
4. 选择第一个满足 `currentInFlight < maxConcurrency` 的 Key
5. 若找到，任务绑定到该 Key
6. 若全部已满，则任务保持平台 `queued`

本轮不做：

- 权重调度
- 按成功率排序
- 按剩余并发最多优先
- Key 失败后自动换 Key 重试

#### 2. 任务记录补充字段

RH 任务记录需要补充：

- `assignedRhKeyId`
- `assignedRhKeyNoteSnapshot`
- `rhQueueReason`

作用：

- 排查任务到底分配到了哪个 Key
- 在 Key 被后续修改备注后，保留任务当时的上下文快照
- 当任务排队时，明确记录是“所有 Key 并发已满”而不是模糊地写成普通队列等待

#### 3. 占用数统计

第一版采用运行态计数即可，不额外引入独立持久化表：

- 依据 RH 在途任务数统计 Key 当前占用
- 包括 `queued-to-key` 与 `running` 这类实际占位任务

如果后续发现重启恢复、跨进程一致性还需要增强，再进入第二轮治理。

#### 4. RH 总并发

后台 RH 平台并发口径改为只读汇总：

- `totalConcurrency = sum(enabled key.maxConcurrency)`

展示值保留在后台运维面板与 RH Key 池摘要中，但不再把 RH 平台总并发当作一个独立人工输入值。

### 三、RH 节点顶部阶段进度条

#### 1. 状态语义

节点新增统一阶段进度显示，规则如下：

- `idle`
  - 不显示进度条
- `submitting`
  - 显示 `5%`
  - 文案：`任务提交中`
- `queued`
  - 显示 `5%`
  - 文案：`任务队列排队中`
- `running`
  - 显示 `45%`
  - 文案：`任务已提交，正在生成`
- `success`
  - 显示 `100%`
- `failed`
  - 显示失败态，不保留中间进度假象

#### 2. 前后端职责

后端负责归一化状态与阶段进度口径，前端只消费：

- `status`
- `progress`
- `queueHint`

不允许节点前端自行根据零散字段再猜测一套状态逻辑，以免和 RH Worker / API 的真实运行态分叉。

#### 3. 与已有节点视觉对齐

这条进度条要尽量复用当前图片等生成节点的视觉语言：

- 顶部进度区
- 颜色与状态一致
- 失败态与停止态沿用现有语义

但本轮不做新的复杂动画系统。

### 四、RH 节点参数区收口

#### 1. 默认隐藏技术描述

画布参数区默认不展示以下信息：

- `来自 requestExample.nodeInfoList 的 xxx.xxx`
- 类似的字段来源描述
- 仅对后台分析阶段有意义的原始技术注释

这些内容继续保留在 RH 后台工作台中，供管理员检查和修订。

#### 2. 显示名优先级

前台参数显示名采用：

1. `displayLabel`
2. `label`
3. `fieldName`

也就是说，后台一旦填了更友好的备注名，前台就以备注名为准；只有没有填写时才退回原始字段名。

#### 3. 参数区保留内容

前台参数区默认保留：

- 参数名
- 类型标签
- 必填 / 可选
- 当前值或输入控件

这一轮不把“技术详情折叠开关”作为必须项；如果实现时发现前台仍需少量调试信息，可作为后续补充项。

### 五、后台 RH 分析与字段生成的职责边界

从 `requestExample.nodeInfoList` 自动生成字段仍然保留，但生成逻辑职责重新明确：

- 对后台管理员：
  - 自动生成 `nodeId / fieldName / valueType / required / defaultValue`
  - 可带来源描述，方便核对
- 对前台画布用户：
  - 只消费处理后的显示名、类型和输入控件
  - 不直接暴露来源注释

这意味着“字段生成能力保留，字段展示方式收口”，而不是删除后端已有的分析信息。

### 六、AGENTS 中补入 RTK 协作规则

在仓库 `AGENTS.md` 中新增专门规则块：

- 执行 shell 检索、读文件、目录查看、git 状态、差异查看、构建脚本与测试命令时，默认优先使用 RTK
- 常见形式：
  - `rtk read`
  - `rtk grep`
  - `rtk find`
  - `rtk git status`
  - `rtk git diff`
  - `rtk npm run <script>`
- 以下情况允许回退普通命令：
  - RTK 不支持
  - 需要完整原始输出
  - 需要实时流式或交互行为
- 若回退普通命令，需把原因视为“RTK 不适用”，而不是忽略这条规则

这条治理项属于仓库协作规则更新，不属于 RH 产品功能本身，但和本轮实施过程直接相关，因此纳入同一设计。

## 数据与接口调整建议

### 后台接口

RH Provider 读写接口需要支持：

- 读取 `rhKeyPool`
- 保存单个或多个 Key
- 单条删除 Key
- 返回脱敏 `apiKeyPreview`

### RH 运行提交接口

RH 任务创建阶段需要：

- 选择实际使用的 `rhKeyPool` 项
- 将所选 Key 的标识写入任务记录
- 若无可用 Key，则明确进入 `queued`

### RH 查询接口

RH 查询响应建议统一带回：

- `status`
- `progress`
- `queueHint`
- `assignedRhKeyId`（仅后台或日志使用时可见）

前台节点只消费对用户必要的字段。

## 错误处理

### 1. 没有任何启用 Key

直接返回错误：

- `RunningHub 未配置可用 Key`

不进入普通排队。

### 2. 启用 Key 都已满

任务进入 `queued`，并返回：

- `任务队列排队中`
- `rhQueueReason = all_keys_busy`

### 3. Key 无效或无法解密

本轮直接按任务失败处理，不自动切换其他 Key 重试。原因是第一版先保证状态可解释，避免把真正的认证错误掩盖成资源切换行为。

### 4. 后台删除正在使用的 Key

删除只影响后续新任务。已分配到该 Key 的在途任务继续按已有任务记录执行，不做中途迁移。

## 决策总结

本轮设计的最终决策如下：

- RH Key 池放在 RH 工作台右侧编辑区的下侧，采用默认折叠卡片
- Key 支持单条新增、编辑、启停与删除
- RH 总并发由启用 Key 的最大并发自动汇总
- RH 调度采用“稳定顺序扫描 + 只选有空余并发的 Key”
- RH 节点进度条采用阶段型进度：`5% / 45% / 100%`
- RH 参数区默认隐藏技术来源描述
- 后台备注名优先覆盖前台参数名显示
- `AGENTS.md` 增加 RTK 默认使用规则
