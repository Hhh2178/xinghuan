# Shared Resource Library And Clean Workflow Export Design

## 目标

本轮设计同时收口三类已经明确的需求：

- 保存到资源库、导出工作流、输出工作流时，要生成“干净模板”，清理旧会话、旧输出和旧任务运行态。
- 在现有个人资源库之外，新增一套所有人可见可用、仅管理员可写的公共资源库，并且保持独立存储。
- 生成库的卡片交互与完整预览能力要向资源库对齐，避免继续成为风格和能力都割裂的一套临时面板。

本轮设计目标不是做一次大重构，而是在不打断当前画布、资源库、生成库主链路的前提下，把模板语义、共享资源能力和素材交互边界立住。

## 本轮要解决的问题

### 1. 工作流模板仍会带入旧运行态

当前导入与恢复链路已经开始清理部分 `LLM` 旧会话残留，但“保存工作流”“导出工作流”“输出工作流”这几个生成模板的入口，仍可能把历史回复、旧输出、RH 任务状态、轮询态和旧报错一起带进模板。

这会导致两个问题：

- 模板不是“干净可复用模板”，而是“带脏运行态的工作快照”。
- 用户在重新导入或分享工作流时，会误以为旧结果是当前模板的一部分。

### 2. 当前资源库只有“个人库”维度

现有资源库本质上是用户私有长期素材库，无法承载：

- 全员可见可用的共享素材
- 管理员集中维护素材母版
- 共享工作流、共享姿势、共享素材集等团队协作场景

如果继续把共享资源硬塞进个人库逻辑里，后续权限、治理、复制语义和后台管理都会越来越混乱。

### 3. 公共资源需要保留引用索引，而不是全部展开成脱库快照

用户已经明确要求：如果工作流中使用了公共资源库的资源，保存/导出模板时需要保留它对公共资源的指向索引。

这意味着模板不能只剩下裸 `fileUrl`，而要知道：

- 它引用的是哪一条公共资源
- 资源来源是公共库还是个人库
- 当资源仍存在时，应该优先恢复成资源索引引用

### 4. 生成库交互与资源库分叉

当前生成库虽然已经具备基础预览层，但仍存在明显问题：

- 卡片按钮结构与资源库不一致
- 预览体验仍偏独立实现
- 图片、视频的完整展示能力不够稳
- 卡片视觉风格和交互密度明显比资源库差

继续在生成库局部补丁，会让资源相关 UI 越来越分叉。

## 设计原则

### 1. 模板保存语义要统一

无论用户触发：

- 保存工作流到资源库
- 导出工作流
- 输出工作流

都应该生成同一种语义的模板：

- 保留结构、配置、手工输入和资源引用
- 清空运行态、旧结果、旧任务状态和历史会话

不能继续出现“导入时清、导出时不清”的分裂行为。

### 2. 公共资源库与个人资源库平行，而不是附着

本轮不采用“在个人资源项上加一个 `shared` 布尔字段”的方案，而采用：

- 个人资源库
- 公共资源库

两套平行资源域。

这样做的收益是：

- 存储隔离
- 权限隔离
- 后续后台管理、统计、迁移、审计都更清楚

### 3. 前台以使用为主，后台以治理为主

公共资源库首版采用：

- 前台双库浏览
- 管理员前台轻编辑
- 后台完整管理

不把画布前台做成完整后台，也不把所有高频操作都强行塞回后台。

### 4. 生成库与资源库要开始共用视觉和交互壳

本轮不一定一次性把三个库完全合并成同一抽屉，但至少要收口：

- 卡片结构
- 动作按钮风格
- 悬停小眼睛预览
- 完整图片/视频预览层

后续共用组件要优先于继续复制粘贴两套实现。

## 方案比较

### 方案 A：最小改动方案

做法：

- 只补工作流导出清理
- 公共资源库仍复用现有个人资源库存储，只加 `scope`
- 生成库只做样式微调

优点：

- 改动面最小

缺点：

- 公共资源和个人资源仍然混在一起
- 权限和复制语义不清
- 生成库和资源库仍不会真正收口

结论：

- 不采用

### 方案 B：中等收口方案

做法：

- 新增统一模板运行态清理器
- 公共资源库采用独立存储，前台双库浏览
- 管理员前台保留上传按钮和轻编辑，后台保留完整管理
- 生成库卡片与预览向资源库对齐，并开始抽共用壳

优点：

- 能同时解决模板语义、共享素材和生成库体验问题
- 边界清楚，不需要一次性重写整套资源系统
- 可平滑接入现有资源库和生成库接口

缺点：

- 需要同时改 `apps/web`、`apps/api`，并补一层公共资源的数据访问

结论：

- 采用本方案

### 方案 C：资源资产系统大重构

做法：

- 直接把个人资源库、公共资源库、生成库和工作流导出统一成完整资产系统

缺点：

- 范围明显超过本轮目标
- 风险高，回退成本大

结论：

- 本轮不采用

## 范围与非目标

### 范围内

- 保存工作流到资源库时清理所有运行态残留
- 导出工作流时清理所有运行态残留
- 输出工作流时清理所有运行态残留
- 保留模板中的资源引用索引，尤其是公共资源引用
- 新增公共资源库的独立读写能力
- 公共资源库支持当前资源库已有全部类型：
  - `image`
  - `video`
  - `audio`
  - `set`
  - `pose`
  - `workflow`
- 前台资源浏览中新增 `我的资源库 / 公共资源库`
- 管理员在公共资源库前台有明确的 `上传到公共资源库` 按钮
- 管理员在公共资源卡片上具备轻编辑能力：
  - 重命名
  - 改分类
  - 改标签/备注
  - 删除
- 普通用户可以把公共资源 `另存为我的资源`
- 生成库卡片操作与预览向资源库对齐

### 非目标

- 不把生成库与资源库底层立刻合并成同一张总资产表
- 不做公共资源审核流、上下架流或部门级权限
- 不做批量上传、批量移动、批量删除
- 不做公共资源删除时的强阻断引用分析
- 不在本轮做资源系统彻底重构

## 详细设计

### 一、统一“干净模板”导出语义

#### 1. 适用入口

以下三类入口统一采用同一套模板清理逻辑：

- 保存工作流到资源库
- 导出工作流
- 输出工作流

这三类入口不再各自散落拼装模板数据，而是都走同一套“模板导出清理器”。

#### 2. 清理范围

本轮按“清理所有运行态残留”的口径处理，包括但不限于：

- `LLM` 历史会话
- `LLM` 回复内容
- 旧生成结果
- 旧图片/视频/音频输出数组
- RH / RunningHub 的任务状态
- RH / RunningHub 的轮询状态
- 旧报错态
- 旧进度态
- 旧任务 id、运行 id、结果缓存

清理后的模板应保持：

- 节点结构
- 连线结构
- 用户配置
- 模型配置
- 输入参数
- 手工填写内容
- 资源引用信息

#### 3. 资源引用保留语义

如果节点当前使用的是资源库素材，模板中不应只保留裸文件地址，而应尽量保留资源引用索引：

- `resourceSource`
  - `personal`
  - `shared`
- `resourceItemId`
- `resourceKind`
- `fallbackUrl`

恢复优先级：

1. 优先按 `resourceSource + resourceItemId` 解析资源引用
2. 若资源还存在，则恢复成资源索引使用态
3. 若资源不存在，但有 `fallbackUrl`，则可退化到裸地址
4. 若两者都不可用，则提示资源缺失

#### 4. 为什么不展开成脱库快照

如果公共资源模板在保存时被全部展开成一堆裸地址：

- 后续公共资源更新无法被模板感知
- 共享资源治理能力会丢失
- 用户也无法明确知道该素材来自公共库

因此公共资源模板要保留对共享库的显式引用。

### 二、公共资源库数据模型

#### 1. 资源域划分

本轮资源系统分为三类来源：

- 个人资源库
- 公共资源库
- 生成库

其中：

- 个人资源库：用户私有长期素材
- 公共资源库：全员可读、管理员可写的共享长期素材
- 生成库：用户私有短期生成素材

#### 2. 公共资源库类型范围

公共资源库首版覆盖与个人资源库相同的全部资源类型：

- `image`
- `video`
- `audio`
- `set`
- `pose`
- `workflow`

这样可以避免首版只支持部分类型，后续再补一轮类型分叉。

#### 3. 公共资源项结构

公共资源项结构与个人资源项尽量保持同构，便于前台列表和卡片复用：

- `id`
- `kind`
- `categoryId`
- `title`
- `originalName`
- `fileUrl`
- `thumbUrl`
- `mime`
- `size`
- `tags`
- `favorite`
- `materialSetKind`
- `materialSetItems`
- `workflowFragment`
- `workflowNodeCount`
- `workflowEdgeCount`
- `workflowPreview`
- `revision`
- `createdAt`
- `updatedAt`

共享域额外建议字段：

- `note`
- `publishedBy`
- `publishedAt`

#### 4. 独立存储

你已经要求“独立数据库”，因此本轮设计不采用与个人资源库混写的模式。

首版具体实现可根据当前后端存储现实落成：

- 若资源库仍主要由独立 ledger 驱动，则新增共享资源 ledger
- 若已适合落 PostgreSQL，则新增独立共享资源表域

但无论具体介质如何，语义上都应满足：

- 共享资源独立存储
- 共享资源独立读写逻辑
- 不与个人资源条目混写

### 三、前台双库浏览与管理员轻编辑

#### 1. 浏览结构

前台资源浏览默认采用双库浏览：

- `我的资源库`
- `公共资源库`

生成库可以继续保留独立入口，但其卡片和预览交互要向资源库对齐。

#### 2. 普通用户在公共资源库中的能力

所有已登录用户都可以：

- 浏览公共资源
- 搜索
- 分类筛选
- 插入画布
- 发送使用
- `另存为我的资源`

#### 3. 管理员在公共资源库中的能力

管理员在前台公共资源库视图中额外拥有：

- 一个显式的 `上传到公共资源库` 按钮
- 资源卡片上的轻编辑动作：
  - 重命名
  - 改分类
  - 改标签/备注
  - 删除

本轮不在前台引入完整的后台式管理面板，只保留高频轻操作。

#### 4. `另存为我的资源`

从公共资源执行 `另存为我的资源` 时，其语义不是简单共享同一条数据库记录，而是创建当前用户的个人副本：

- 媒体类复制引用与元数据
- `set / pose / workflow` 复制结构化内容
- 新记录属于当前用户
- 后续个人修改不影响公共资源原件

### 四、后台公共资源重管理

后台 Admin 侧新增独立的公共资源管理板块，承担：

- 全量列表浏览
- 分类管理
- 搜索和过滤
- 编辑标题、分类、标签、备注
- 删除资源
- 后续扩展审计、批量整理和更强治理能力

职责边界明确为：

- 前台：创作现场的浏览、使用、轻维护
- 后台：整理、治理、查阅、后续扩展能力

### 五、生成库交互与预览统一

#### 1. 卡片动作统一

生成库卡片动作顺序收口为：

- 预览
- 下载
- 插入
- 删除

按钮风格和资源库靠拢，避免继续保留当前比较割裂的按钮布局。

#### 2. 悬停预览

保留资源库现有“小眼睛悬停看大图”的交互感知，并让生成库也采用同样的交互方式。

#### 3. 完整预览层

图片和视频在点击后进入完整预览层，展示要求：

- 图片：`object-contain`，显示完整比例，不自动裁切
- 视频：完整容器展示，支持播放控件，不自动裁切主内容

这层应优先抽成共用预览组件，而不是让生成库和资源库各自保留一套预览层逻辑。

#### 4. 为什么这轮要抽共用壳

如果本轮只是把生成库“改得像资源库”，但不抽出共用卡片与预览壳，后续：

- 资源库改一次
- 生成库再跟一次
- 预览层继续分叉

维护成本会越来越高。

### 六、权限边界

#### 1. 普通用户

- 可读：
  - 我的资源库
  - 公共资源库
  - 生成库
- 可写：
  - 我的资源库
  - 生成库中的个人操作
- 不可写：
  - 公共资源库

#### 2. 管理员

- 拥有普通用户全部能力
- 可写公共资源库
- 可在前台执行上传和轻编辑
- 可在后台执行完整管理

#### 3. 后端硬权限

公共资源库必须按读写分离进行权限控制：

- 读接口：所有已登录用户可调用
- 写接口：仅管理员可调用

不能只依赖前端隐藏按钮作为权限控制。

## 错误处理与兜底

### 1. 公共资源引用缺失

当模板中的 `shared resource` 引用已失效时：

- 若有 `fallbackUrl`，允许退化为裸资源地址
- 若无 `fallbackUrl`，明确提示资源缺失

### 2. 公共资源删除

首版不强拦截“该资源已被模板引用”的删除行为，但在后台或管理员前台删除时，建议提示：

- 该共享资源可能已被工作流模板引用

### 3. 复制到个人资源失败

`另存为我的资源` 失败时，前台要返回清晰错误，而不是让用户误以为已经保存成功。

### 4. 模板清理过度

若某类节点在模板清理后被误删了用户配置，必须能只回退清理器逻辑，而不影响资源库和生成库其他改动。因此模板清理应做成独立函数，而不是分散写在多个保存入口里。

### 视觉与体验验收

按当前仓库规则：

- Agent 负责代码、架构、运行态与契约层验证
- 最终视觉与交互观感验收由用户完成

## 实施顺序建议

1. 先收口模板导出清理器，统一保存/导出/输出工作流的语义
2. 补公共资源库的数据模型、接口与权限控制
3. 在前台资源库中加入双库浏览与管理员上传按钮
4. 实现公共资源 `另存为我的资源`
5. 抽生成库与资源库的共用卡片/预览壳
6. 完善文档、契约脚本与验证记录

## 决策总结

本轮设计最终决策如下：

- 工作流保存、导出、输出统一生成“干净模板”
- 清理所有运行态残留，而不是只清 `LLM`
- 模板中保留资源引用索引，尤其是公共资源引用
- 公共资源库与个人资源库平行，且采用独立存储
- 公共资源库首版覆盖全部现有资源类型
- 前台采用双库浏览，管理员在公共资源页签有显式上传按钮和轻编辑能力
- 普通用户可将公共资源 `另存为我的资源`
- 后台保留公共资源的完整治理入口
- 生成库交互与预览向资源库对齐，并优先抽共用壳
