## 1. 本轮问题定义

当前实现完成了 Assistant Conversation、Canvas Run 和 Admin Governance 的技术拆分，但没有形成可用的产品交互。主要偏差不是单纯“样式不好看”，而是把内部数据结构和运行投影直接暴露给用户：

1. AI 助手像调试窗口，不像创作助手。内部 JSON、过多元信息、粗糙滚动区域和弱层级占据主体。
2. 悬浮入口和窗口都固定，不能拖动、停靠或记忆位置，容易遮挡无限画布内容。
3. Markdown 仅做基础文本渲染，缺少面向结果的语义块、块级复制和可扫描结构。
4. AI 托管从“生成计划”直接跳到“开始托管”，缺少任务目标、范围、约束、预期结果、计划确认和可理解的执行解释。
5. 失败只显示笼统状态。用户看不到失败节点、真实原因、影响范围和修复动作。
6. Admin 将角色、路由、工具、知识、质量、恢复等数据模型做成等权表单集合，缺少围绕管理员任务组织的导航、工作流和发布心智模型。

## 2. 已确认的用户需求

### 2.1 AI 助手

- 保持深色视觉体系，但不沿用当前窗口的布局和视觉细节。
- 参考腾讯云智能助手的轻量层级、留白、初始欢迎区、快捷任务和紧凑输入区，不复制其白色皮肤。
- 当前顶部横向上下文滑轨移除。
- 空会话顶部显示一组清晰的快捷按钮；开始输出后，该区域自动折叠，不长期占用对话空间。
- 悬浮球必须可拖动，且不能只能固定在一个角落。
- 助手窗口必须可拖动；需要处理视口边界，不能拖出屏幕后无法找回。
- Markdown 输出必须按内容类型形成视觉不同的渲染块。
- 各结果块右上角提供小型复制按钮，并有明确复制反馈。
- 移除无价值的小字备注；正文和关键状态字号必须可读。
- 重新设计滚动区域和滚动条；不需要的横向滚动、滑槽和嵌套滚动直接移除。

### 2.2 AI 托管

- 托管不是单按钮运行器。开始前必须让 AI 和用户都明确“要完成什么”。
- 用户需要看到 AI 对画布的理解、拟执行范围、计划、当前状态、关键判断和下一步。
- 运行中的解释必须是受控的状态、依据与决策摘要，不泄露 Provider reasoning、隐藏思维链或内部上下文。
- 失败必须显示具体失败节点、用户可理解的原因、受影响的后续步骤和可执行修复方案。
- 日志不能是唯一信息载体；计划、步骤、产物、审批、异常和恢复需要不同的交互结构。

### 2.3 Admin

- 当前 Agent 后台的整体信息架构和页面构思不被接受，不能只做配色、间距或组件层面的修补。
- 后台必须先重新对齐管理员的实际目标、对象关系和发布流程，再决定页面、导航和编辑器结构。
- 角色、提示词、模型路由、知识、工具、质量、恢复、运行和审计不应默认作为十一个等权页面直接铺开。

## 4. AI 助手目标体验草案

### 4.1 产品角色

AI 助手是“当前画布的创作协作者”，负责问答、解释、分析、建议、草拟和形成可确认的修改提案。它不是 Canvas Run 监控器，也不是内部 JSON 查看器。

### 4.2 窗口与定位

- 悬浮球支持拖动，并在释放时吸附到最近的左右安全边缘；这是助手窗口的唯一锚点。
- 助手窗口始终从悬浮球旁展开，不允许脱离悬浮球成为完全独立的浮窗。
- 悬浮球位置按用户和设备记忆；窗口尺寸按设备记忆，尺寸变化后自动校正回可见区域。
- 助手窗口以标题栏作为明确拖动把手，但拖动只改变相对锚点的偏移；按钮、输入框、内容选择不触发拖动。
- 助手窗口与 AI 托管面板采用避让布局：打开或移动任一面板时，系统计算两个面板的安全矩形，自动选择不重叠的展开方向或收窄可用尺寸；禁止通过 z-index 让一个面板覆盖另一个面板。
- 桌面端支持移动与有限尺寸调整，并持久化窗口位置和尺寸。
- 当前设计与视觉验收只面向 PC；验收矩阵仅包含 `1920x1080` 与 `2560x1440`。既有窄屏兼容不主动破坏，但不作为本轮设计或验收范围。
- 最小化只隐藏窗口，不结束会话；关闭与新建会话必须有不同语义。

### 4.3 空会话

- 进入后显示简短欢迎语、当前画布名称或选择摘要，以及一个唯一的高价值快捷动作：`分析节点报错原因`。
- 该动作必须优先读取当前选中节点；没有选中节点时，回退到最近一次失败 Run 的失败节点；两者都不存在时，按钮置为不可用并提示先选择节点或打开失败运行。
- 触发后自动附带节点标识、最近失败步骤、错误码、相关配置摘要和上下游阻塞影响，但不把原始 JSON 直接塞进用户消息。
- 结果必须给出四项：发生了什么、为什么发生、影响了哪些步骤、现在可以怎么修复；可直接跳转到节点配置或从失败步骤重试。
- 快捷区只存在于空会话或明确返回首页时；首条消息发送或开始响应后折叠。
- 原横向上下文滑轨删除。上下文改为输入区附近的紧凑附件/范围入口，需要时展开。

### 4.4 对话与内容渲染

- 用户消息保持紧凑；助手结果以内容为中心，不重复显示无价值身份和状态小字。
- 普通说明、步骤、提示、警告、引用、表格、代码、JSON、Canvas Patch Proposal、诊断和计划使用不同语义块。
- 结构化内部对象不得原样倾倒。JSON 仅在用户主动查看技术详情时使用代码块展示。
- 整条助手回答提供一个总复制入口。
- 只有可独立复用的结果块在右上角提供块级复制：代码/JSON、故障诊断、操作步骤、配置建议、Canvas 修改提案和表格。
- 普通标题、单句话、正文段落和短引用不单独显示复制按钮，避免重复操作图标干扰阅读。
- 代码块复制原始代码，表格复制 Markdown 或 TSV，计划/诊断块复制其完整文本。
- 复制成功提供短暂图标/tooltip 反馈，不新增占空间的提示行。
- 流式响应期间保持稳定布局；块完成后才出现最终动作，避免按钮反复跳动。
- reasoning 与最终回答严格隔离。允许显示 `正在检查连接`、`已验证 4 个节点` 等受控过程事件，不显示隐藏推理正文。

### 4.5 排版和密度基线

- 正文默认不小于 `14px`，舒适行高约 `1.6`。
- 次要元信息原则上不小于 `12px`，且只在影响判断时出现。
- 标题、正文、引用和数据使用明确但克制的对比，不以大量边框和小标签制造层级。
- 对话区只保留一个主纵向滚动容器；正常内容不得产生横向滚动。
- 代码和确实不可换行的数据允许在其自身块内横向滚动，滚动条必须细且不抢视觉焦点。

## 5. AI 托管目标体验草案

### 5.1 产品角色

AI 托管是“成熟工作流之上的意图驱动执行代理”。用户一次描述一个或多个创作方向，AI 将需求拆成可执行分支，给成熟工作流填入内容和参数，逐阶段运行、判断产物、衔接下游，并在受控策略内自动恢复，直到交付结果或遇到必须由用户决定的阻塞。

它不是助手的一个 Tab，不是普通的“运行全部节点”，也不是把数据库步骤列表放进悬浮面板。普通工作流运行负责忠实执行既定参数；AI 托管在其上增加需求理解、任务拆解、内容生产、批次编排、质量判断和受控恢复。

### 5.2 核心适用前提

- AI 托管优先作用于已经成熟并发布的工作流，而不是尝试理解任意、未完成、未标注的画布。
- 成熟工作流必须声明输入变量、阶段、输入/输出类型、必选参数、允许的模型/服务商、回退顺位、质量门槛、预算边界和最终交付物。
- AI 可以填写和改写被工作流明确开放的变量，但不能随意改变拓扑、绕过权限或使用未发布模型。
- 当前打开的画布如果是成熟工作流的实例，可直接作为运行目标；否则需要先选择/匹配一个已发布工作流，或提示当前画布不具备托管条件。

### 5.3 视频生成案例：目标运行模型

用户输入多个方向，例如角色、场景、情绪或广告创意后，AI 托管应执行以下流程：

1. `需求解析`：识别共同约束与各方向差异，确认方向数量、交付规格和缺失信息。
2. `批次展开`：每个方向形成独立工作分支，共享用户确认的品牌、人物、尺寸、时长等全局约束。
3. `文本编排`：为每个分支生成或改写图片提示词、负面约束、视频动作/运镜提示词和必要的衔接文本。
4. `图片阶段`：按工作流生成候选图片，记录实际模型、服务商、参数、成本和产物引用。
5. `图片判断`：执行技术有效性检查和视觉质量/一致性评分；按策略自动选优，低置信度时请求用户确认。
6. `视频适配`：把选中图片和原始方向转成对应视频模型需要的提示词与参数，而不是机械复用图片提示词。
7. `视频阶段`：提交视频生成，持续跟踪异步任务，成功后进入质量检查。
8. `错误恢复`：区分网络/限流/服务异常、参数错误、内容策略、模型不可用和质量不达标；按已发布顺位重试服务商、模型或受控参数。
9. `完成交付`：按方向聚合图片、视频、使用的配置、失败/恢复记录和最终选择结果。

### 5.4 多方向任务模型

- 一个托管会话包含一个用户目标和多个 `方向分支`，不是把多段提示词拼成一个节点输入。
- 每个方向分支拥有独立状态、产物、成本、重试预算和终态；一个方向失败不应默认取消其他方向。
- 共享阶段只执行一次；方向相关阶段按配置并发或排队，遵守用户、模型和服务商并发限制。
- 用户可以暂停/取消单个方向，也可以控制整个托管会话。
- UI 同时提供会话总览和方向分支视图，避免把所有步骤混成一条长日志。

### 5.5 AI 自动决策边界

AI 在以下条件内可以自动执行：

- 根据用户方向生成和改写文本、图片提示词与视频提示词。
- 将工作流开放变量映射为具体参数。
- 在已发布、兼容且经过排序的服务商/模型候选中进行故障回退。
- 在预算、次数和质量阈值内重试或选择候选产物。
- 跳过被工作流标记为可选、且不影响交付合同的步骤。

以下情况必须暂停并请求用户确认：

- 需求存在会改变最终方向的关键歧义。
- 需要超出预算、重试次数或工作流允许范围。
- 所有已批准候选模型/服务商均不可用。
- 需要改变工作流拓扑、替换不兼容模型或降低明确质量标准。
- 内容策略、权限、输入所有权或高风险工具操作阻止继续。

### 5.6 开始前：任务简报

托管入口打开后，第一屏应先形成任务简报，而不是立即要求生成/开始：

- 任务目标：用户希望最终得到什么。
- 执行范围：整个画布、选中分组、选中节点下游或自定义范围。
- 完成标准：期望产物、数量、质量或终止条件。
- 约束：成本上限、最长时间、允许使用的模型/工具、禁止修改项。
- 审批策略：关键步骤确认、异常时确认或在预算内自动执行。
- 质量策略：是否生成候选、如何选择、是否允许自动恢复。

AI 可从当前画布和用户自然语言生成简报草案，但用户必须能看懂、修改并确认。

### 5.7 计划确认

- 计划应以阶段和结果组织，而不只是内部节点序号。
- 每个阶段显示目的、涉及节点、输入来源、预期输出、模型/服务、预计成本和风险。
- 预检集中显示阻塞项、警告和可自动修复项。
- 未通过阻塞预检时禁用开始按钮，并提供直接修复入口。
- 用户确认后锁定 revision、配置、知识、预算和审批快照，并清楚说明后续画布编辑不会隐式改变本次 Run。

### 5.8 运行中

- 顶部持续显示当前目标、总进度、当前阶段、耗时和成本。
- 主区优先显示“现在正在做什么、为什么需要这一步、完成后得到什么”。
- 阶段时间线与画布节点保持可定位关系；点击步骤可聚焦对应节点。
- 结果产物、候选比较、审批、异常和恢复各用专门卡片，不混入短日志列表。
- 事件流作为可展开的技术详情存在，不作为默认主视图。
- 暂停、继续、取消、接管和重试的可用条件与影响必须明确。

### 5.9 失败与恢复

- 失败摘要回答四件事：哪里失败、为什么、已完成什么、下一步能做什么。
- 技术错误码进入折叠详情；默认显示经过映射的业务解释。
- 恢复动作按风险排序：自动修复并继续、修改配置后重试、换用已批准备选、跳过非关键步骤、停止并保留已完成结果。
- 从失败步骤重试必须保留成功步骤和产物，除非输入或配置变化使其失效。

## 6. Admin 重构方向：等待业务对齐

### 6.1 已确认的问题

- 当前实现按后端实体拆页面，而不是按管理员任务组织。
- 配置字段、版本状态和发布动作混在同一密集表面，用户无法形成“编辑什么、影响什么、何时生效”的稳定心智模型。
- 技术名词、Key、revision 和内部状态过早暴露，主任务被工程细节淹没。
- 缺少从“定义 Agent”到“测试”再到“发布和观察”的完整工作流。

### 6.2 建议的任务层级（未确认）

建议先收敛为四个管理员工作域，而不是十一个等权入口：

1. `Agent 工作室`：创建 Agent、角色与行为、系统指令、能力组合、知识和模型策略。
2. `测试与发布`：测试场景、配置差异、审核、Gray/Production 发布与回滚。
3. `运行与干预`：运行记录、异常、审批、恢复、成本和质量结果。
4. `平台资源`：模型路由、知识源、工具策略、节点能力等可复用平台对象。

这只是用于对齐的第一版信息架构。需要先确认后台的主要使用者和前三个最高频任务，才能进入线框设计。

## 7. 早期版本收敛：参数化工作流上的 AI 托管

### 7.1 为什么要降 scope

当前“自然语言多方向创作代理”同时要求意图规划、工作流选择、拓扑编排、内容改写、媒体质量判断、批次调度和跨 Provider 恢复。以现有基础直接实现，任何一层不完整都会表现为“AI 会说，但任务不能稳定完成”。早期版本先验证最有价值且边界清晰的闭环：

> 用户为已发布的成熟工作流填写本次变量并启动运行；AI 托管持续监测生成状态，基于明确错误执行受控调整与重试，并在工作流声明的候选产物中选择最符合用户输入和提示词的结果。

### 7.2 MVP 包含

- 当前画布必须引用一个已发布的成熟工作流定义；不做任意画布的自由托管。
- 工作流发布前声明可供用户填写的输入变量和变量绑定。
- 用户通过工作流变量总节点或各输入节点的变量面板填写本次值；AI 托管不承担通用需求拆解和变量自动填写。
- 开始前执行变量完整性、类型、模型目录记录、权限、revision 和预算预检。
- 运行期间展示阶段状态、当前节点、产物、错误原因、恢复动作和最终结果。
- 对已发布的兼容模型/服务商执行有限顺位回退；每次回退都记录原因和实际选择。
- 对明确标记为候选集合的多个生成素材，结合用户变量、实际提示词和质量规则进行排序，选中项进入下游，未选中项在选择门之后标记为 `not_selected`。

### 7.3 MVP 不包含

- AI 自由选择或修改工作流拓扑。
- AI 在多个工作流之间自行编排。
- 任意节点自动新增、删除、重连或改变端口类型。
- 未经工作流作者声明的多方向批量展开。
- 任意位置的自动选片和复杂候选合成；只在显式选择门上执行候选判断。
- 复杂的跨阶段 Agent 角色网络。

## 8. 工作流变量设计

### 8.1 核心原则

变量是工作流的公开输入合同，不是散落在节点 JSON 里的临时占位字符串。工作流发布时冻结变量 schema 和绑定；每次运行创建独立的 input snapshot，历史运行不随工作流后续编辑变化。

### 8.2 工作流输入声明

早期版本支持：`text`、`image`、`video`、`audio`、`number`、`select`。每个变量至少包含 `key`、用户可见名称、类型、是否必填、默认值、描述、约束、是否允许 AI 填写、是否允许 AI 改写和发布版本。内部 ID、Provider Key 和文件路径不能成为用户变量。

变量名称在单个工作流内唯一。同一工作流不同节点出现相同的 `##变量名##` 时，必须解析为同一个 workflow-level variable；一次修改同步影响全部引用。需要不同值时必须使用不同变量名。名称比较需要统一去除首尾空格并执行稳定的大小写/Unicode 归一化，禁止创建视觉相同但内部不同的变量。

### 8.3 节点字段的变量开关

- 关闭：字段保持固定值，运行时不可被 AI 改写。
- 整字段绑定：字段值完全来自一个同类型工作流变量。
- 模板绑定：字段由固定文本和一个或多个变量片段组成。

发布时解析模板 AST，拒绝未知变量、类型不兼容变量、非法表达式和缺少必填变量的绑定。运行时只使用发布版本的绑定快照。

### 8.4 文本节点设计

文本节点的 `prompt` 字段支持三种模式：

1. `固定文本`：不可变的工作流指令。
2. `整段变量`：整个 prompt 来自一个 `text` 变量。
3. `模板文本`：固定句式中插入变量，适合“固定制作规范 + 用户主题/角色/风格”。

文本变量采用用户确认的 `##变量名##` 输入语法。用户输入成对井号并完成变量名后，编辑器将整段转换为黄色底纹、高对比文字的内联 token；token 仍处于文本流中，可选中、删除、移动和重命名。

`##变量名##` 只是编辑和导出语法，内部必须保存稳定 variable ID 和结构化 token 范围，不能在运行时用正则做裸字符串替换。变量改名后所有引用同步更新显示名；未闭合、未知或重复冲突的 token 使用红色错误态。需要输入字面量 `##` 时使用明确的转义或“作为普通文本”操作。

开启变量模式后，文本输入框下方展开节点内变量面板。面板按当前文本中的首次出现顺序列出变量，每项包含黄色变量标识、变量名称、类型、必填状态、本次值/默认值输入和绑定状态。面板使用自然高度，不制造节点内嵌套滚动；变量较多时按分组折叠，并保持错误项可见。

变量面板不是另一份数据源：修改值写入当前工作流运行输入，修改名称或定义写入工作流变量注册表。删除仍被其他节点引用的变量必须提示影响范围并阻止静默删除。

文本变量额外支持单行/多行、长度约束和默认值。提示词审核失败后的 AI 安全改写只能作用于本次运行快照，并展示原值、替换片段、改写值和重试次数；不能静默修改工作流模板或默认值。

### 8.5 上传素材节点设计

上传节点的图像、视频、音频输入分别作为强类型变量入口。变量化后，节点保存 `input.reference_image` 这类绑定，运行快照再解析为当前用户有权访问的素材引用。类型不匹配、素材不存在或权限失效时，开始前阻止运行。

### 8.6 工作流变量总节点

- 每个工作流最多存在一个 `工作流变量` 控制节点；它不参与普通数据连线和生成执行。
- 节点展示全部变量的名称、类型、默认值/本次值、必填和有效状态。
- 每个变量列出所有绑定位置，使用用户可见节点数字编号，例如 `#12 文本.prompt`、`#18 上传.image`；内部仍以稳定 node ID 为权威，避免节点编号变化破坏绑定。
- 点击绑定位置可定位并选中对应节点；修改变量值会同步刷新所有引用 token 的值预览。
- 变量注册表属于工作流 metadata，变量总节点只是其画布编辑器和运行输入入口；删除该节点不应静默删除变量定义，重新添加后可恢复投影。
- 发布工作流时，变量总节点集中展示未绑定变量、缺失默认值、类型冲突和无效节点引用，并阻止带错误发布。

### 8.7 AI 托管在 MVP 中负责什么

- 监测工作流、节点、任务和 Provider 的权威状态，并用可理解的阶段信息展示。
- 对失败进行分类，不把所有失败统一为“运行异常”。
- 对暂时性网络、限流或服务错误先按预算重试原配置，再按节点发布的兼容顺位切换服务商/模型。
- 对提示词审核拒绝，定位高风险片段，生成保持原意的低风险替换文本，仅更新本次 Run snapshot，并在有限次数内重试。
- 对上游失败，优先恢复上游；只有恢复成功后才释放依赖它的下游步骤。
- 在显式候选选择门上，结合用户变量、最终提示词、媒体理解结果和质量规则选择最佳素材。
- 未选中的候选标记为 `not_selected`，其专属下游分支在提交前标记为 `skipped`；已经提交给 Provider 的下游任务不能伪装成“取消成功”。
- 保留实际使用模型、服务商、提示词改写 diff、重试、候选评分和选择原因。

审核拒绝、模型不可用、技术失败和质量不达标必须使用不同恢复策略。AI 不能把任何 Provider 失败都归因于提示词，也不能在没有错误证据时擅自改写用户内容。

AI 在 MVP 中不负责创建新节点、改变连线、选择未经发布的模型或绕过变量类型和权限约束。

### 8.8 AI 助手边界

AI 助手继续作为独立的交互式协作者，首个快捷能力是“分析节点报错原因”。它可以解释错误、回答节点/变量问题，并在用户明确请求时提供文本建议；它不拥有 Canvas Run 状态，不自动执行重试，也不与 AI 托管共享同一个面板。

## 9. 工作流区域：独立运行边界

### 9.1 与普通节点组的区别

- `节点组` 继续负责画布视觉整理和局部执行顺序。
- `工作流区域` 是可独立运行、发布、暂停、恢复和托管的强边界。
- 层级固定为 `Canvas -> Workflow Region -> Execution Group -> Node`。
- 一个节点或节点组在同一时刻最多属于一个工作流区域；MVP 不支持工作流区域互相嵌套。

### 9.2 创建与编辑

- 用户可框选若干独立节点、完整节点组或二者组合，执行“创建工作流区域”。
- 区域拥有稳定 workflow ID、用户可见名称/编号、成员清单、变量注册表、阶段顺序、运行策略和 workflow revision。
- 成员关系必须显式保存，不能只靠节点是否落在矩形内部推断；移动、缩放区域不能静默改变成员。
- 区域边框使用区别于普通节点组的视觉层级，常态克制，选中或运行时才强化状态。
- 将节点移入/移出区域必须是显式动作，并展示变量、连线和运行影响。

### 9.3 运行隔离

- 编译 Workflow Run 时只读取区域成员、内部连线、工作流变量、阶段顺序和发布配置。
- 工作流区域外的节点运行不得改变区域内步骤状态、输入快照或终态；区域 Run 也不得触发外部普通节点。
- workflow revision 只在成员、内部连线、变量、阶段顺序或运行配置变化时递增。外部画布位置和其他区域编辑不应导致当前 Run revision 冲突。
- 每个工作流拥有独立 Run、事件序列、成本、重试预算和终态。切换托管视图不停止后台运行。
- 多个工作流可以同时运行；共享 Provider 并发可能造成排队，但不能造成状态串线、输入串线或错误归属错误。
- 同一工作流默认只允许一个 active Run，除非后续明确增加批次实例能力。

### 9.4 跨边界数据

已确认：为保证隔离，普通边禁止直接穿过工作流边界。跨区域数据只能通过显式的 `工作流输入` 和 `工作流输出` 节点传递，并进入 Run snapshot。发布和开始前必须拒绝未声明的跨边界连线。

- `工作流输入` 将外部素材引用或工作流变量转换为区域内的强类型输入。
- `工作流输出` 只暴露工作流明确声明的最终/中间产物，不泄露内部临时状态。
- 工作流输出连接另一个工作流输入时，只建立显式数据依赖；MVP 不因为产物到达而自动启动另一个工作流。
- 输入/输出节点保存类型、名称、来源、cardinality 和版本；类型不兼容在连线和预检阶段双重阻止。

### 9.5 多工作流托管切换

- AI 托管面板顶部提供工作流目标选择器，显示工作流名称、编号、当前状态和异常数量。
- 打开面板时优先指向当前选中的工作流区域；没有选中时回到最近查看或唯一工作流。
- 切换只改变面板投影和控制目标，不改变任何正在运行的 Run。
- 多个工作流同时运行时提供紧凑总览；所有暂停、重试、取消和顺序编辑动作必须明确显示目标工作流。
- AI 助手与托管面板继续使用几何避让；工作流选择器属于托管面板，不进入助手会话。

### 9.6 区域视觉与颜色

- 工作流区域使用完全不透明的实色背景作为底板，并始终位于成员节点和内部连线下方；区域内不透出画布网格。
- 用户可通过颜色 swatch 和自定义颜色选择器调整底色。颜色变化立即预览并保存在工作流区域视觉 metadata 中。
- 系统根据底色自动选择区域标题、编号、边框和状态文字的深/浅对比色，保证可读性。
- 运行、暂停、失败和选中状态通过边框、标题栏状态和局部标记表达，不用改变整块底色造成视觉闪烁。
- 颜色、位置、尺寸和折叠状态属于视觉属性，不递增 workflow runtime revision，也不使 active Run 失效。
- MVP 禁止工作流区域互相重叠；调整尺寸或移动造成重叠时显示碰撞提示并阻止提交，避免不透明底板遮挡其他工作流。

## 10. 工作流阶段与执行顺序

- 工作流区域内的普通节点组升级为可排序的 `执行阶段`；未分组节点进入显式“未分组阶段”，不能悄悄追加到所有阶段之后。
- 托管面板在运行前提供阶段排序视图，支持拖动调整顺序、串行/并行标记和阶段跳过。
- 拓扑依赖是硬约束，人工顺序是满足依赖后的调度偏好。任何把下游阶段拖到其上游之前的操作都应立即阻止并高亮冲突连线。
- 无依赖阶段可以串行或按并发预算并行；同一阶段内部继续按拓扑排序。
- 顺序在开始时锁入 Run Plan。active Run 期间不能静默改变；需要调整时必须取消/结束当前 Run，再基于新 workflow revision 创建新 Run。
- AI 托管只能遵守已确认顺序，不能为“优化”自行重排阶段。

## 11. 智能候选选择器节点

### 11.1 节点职责

新增 `智能候选选择器`，作为多个上游素材和下游生产节点之间的显式阻断门。现有 `pick-from-set` 继续负责确定性的按索引选择，不能承担 AI 语义选优。

### 11.2 输入与配置

- 候选素材输入：同一类型的多张图片或多个视频；MVP 不混合媒体类型。
- 选择依据输入：独立文本端口，用于连接用户提示词或生成候选时使用的提示词。
- 节点备注：用户填写的选择倾向，例如“优先人物一致性，不要大特写，背景必须保留建筑”。
- 候选产物必须保留生成提示词、变量快照、模型、服务商和上游节点 provenance，避免只靠一个全局文本猜测每个候选的意图。
- 备注和选择依据进入 Run snapshot，AI 助手可在诊断/解释时读取，AI 托管可在选择时读取。
- 选择数量支持 `最佳 1 个` 和有上限的 `Top K`；AI 模式还需设置最低置信度和低置信度时是否请求人工选择。

### 11.3 手动与 AI 模式

- 普通运行默认进入手动选择：候选收齐后暂停在选择门，用户查看预览、提示词和备注后确认。
- AI 托管运行由 AI 自动评分和选择；用户可在下游尚未提交前接管并覆盖选择。
- 节点必须等待所有声明的上游候选到达终态，或达到明确的候选数量/超时条件，不能第一个素材到达后过早选择。
- AI 评分至少覆盖技术有效性、提示词符合度、构图/视觉质量、工作流变量符合度和用户备注符合度，并展示选择摘要和置信度，不展示隐藏 reasoning。

### 11.4 下游裁剪

- 选择器只向下游输出选中素材及其 metadata。
- 未选候选保留在本次 Run 结果中，状态记为 `not_selected`，方便用户查看和重新选择。
- 只依赖未选候选的下游分支在提交 Provider 前标记为 `skipped_by_selection`。
- 已提交或已经运行的任务不能伪装为成功取消；因此选择门必须位于下游任务释放之前。
- 选择结果、候选评分、备注、人工覆盖和最终输出绑定必须可审计、可恢复。

## 12. AI 托管运行设置

### 12.1 入口与布局

- AI 托管面板标题区提供齿轮按钮，打开独立设置 Drawer/Popover；设置面板与主运行时间线不能互相覆盖关键控制。
- 默认只展示高频设置，高级策略折叠；不在主面板堆满开关和小字说明。
- 设置页顶部始终显示当前目标工作流名称、设置来源和“应用到下一次运行”的状态。

### 12.2 基础设置

- `节点默认重试次数`：同一 Provider/模型和同一有效配置下的最大重试次数，允许 `0-10`。
- `重试耗尽后的策略`：`终止工作流` 或 `切换兼容服务商/模型`。
- `最大回退次数`：避免在候选池中无限循环。
- `提示词审核恢复`：是否允许同义低风险改写，以及最大改写重试次数。
- `阶段并发`：无拓扑依赖阶段的最大并发数。
- `运行时限与预算`：总时限、成本上限；超过后停止并保留已完成结果。
- `候选选择`：手动或 AI、Top 1/Top K、最低置信度和低置信度是否转人工。

### 12.3 节点覆盖与兼容回退

- 工作流级重试次数是默认值；高级区允许对指定生成节点设置覆盖值，并以节点数字编号和名称展示。
- “同类型模型”不能只按图片/视频分类。回退候选必须满足节点实际能力、输入模式、比例、时长、文件限制、权限、发布环境和成本约束。
- 回退顺序来自节点或工作流发布的候选链，AI 不能临时搜索并使用未发布模型。
- 回退会突破预算、质量或输入兼容性时，停止并请求用户确认。
- 必选节点耗尽恢复后按终止策略处理；可选节点是否允许跳过必须由工作流作者明确声明，不能由 AI 自行判断。

### 12.4 设置记忆与快照

设置使用四层优先级：

1. 平台安全上限：管理员维护，用户不可突破。
2. 工作流默认策略：随工作流版本发布。
3. 当前用户对当前工作流的记忆设置：按 `owner + workflow ID` 服务端保存，可跨设备恢复。
4. 本次运行快照：开始时冻结，优先级最高且运行中不可静默改变。

- 用户可以“恢复工作流默认值”，也可以将当前值只应用一次而不覆盖记忆设置。
- 不同工作流之间不共享重试、候选或预算设置，避免一个视频工作流的策略污染图片工作流。
- 修改设置不影响 active Run；界面明确提示从下一次 Run 生效。需要改变当前 Run 时必须通过正式暂停/取消/接管流程。
- 每次 Run 记录最终解析后的设置、来源层和覆盖项，便于复现与审计。

## 13. 分阶段路线

- `MVP-0`：工作流变量 schema、`##变量##` token 编辑、文本/上传节点变量面板、变量总节点、发布校验和运行 input snapshot。
- `MVP-1`：Workflow Region、显式成员、不透明可调底色、独立 revision/Run、工作流输入/输出、多工作流托管切换和阶段顺序。
- `MVP-2`：运行监督界面、错误分类、原配置重试、生成节点模型/服务商兼容顺位回退。
- `MVP-3`：提示词审核失败的受控改写、diff、重试预算和恢复证据。
- `MVP-4`：智能候选选择器、手动/AI模式、媒体理解评分、最佳素材选择和未选分支裁剪。
- `Later`：列表变量、多方向分支、工作流自动选择、复杂多 Agent 编排和跨工作流组合。

## 14. 非目标与安全边界

- 不通过显示隐藏思维链来制造“可解释性”。只显示受控的过程事件、证据和决策摘要。
- 不把腾讯云参考图逐像素复制；借鉴其轻量入口、空态节奏和操作收纳方式，并适配无限画布深色工作环境。
- 不以增加更多小标签、说明文字、卡片和边框解决信息架构问题。
- 不在需求未对齐前继续堆叠 Admin 表单或给现有页面做表面换肤。
- Production 在完整 Gray 验收前保持不变。

## 15. 验收原则

- 可用性：用户在不阅读文档的情况下，能说清助手、托管和后台各自负责什么。
- 可控性：悬浮入口与窗口可移动、可恢复、不会遮挡后无法找回。
- 可读性：关键正文和状态在常见桌面分辨率下无需放大即可阅读。
- 可解释性：运行失败时，用户能在一个屏幕内找到失败对象、原因和下一步。
- 运行安全：开始前阻止缺失模型、无权限、revision 冲突和不可执行节点等确定性失败。
- 信息节制：默认界面不暴露内部 JSON、隐藏 reasoning、冗余 ID 或无行动价值的元信息。
- 视觉验证：只在 `1920x1080` 与 `2560x1440` PC 视口执行真实浏览器截图、拖动/缩放/滚动/重连行为验证和重叠检查；其他尺寸不进入验收矩阵。
- 隔离性：一个工作流区域外的节点、变量、Run 和错误不会进入其运行快照或托管视图。
- 顺序安全：用户不能保存违反拓扑依赖的阶段顺序，AI 不能绕过已锁定顺序。
- 选择安全：未选素材不会释放其专属下游任务，低置信度选择按策略停留在人工确认门。
- 设置稳定性：用户记忆设置按用户和工作流隔离，active Run 始终使用开始时冻结的有效设置。
- 视觉边界：工作流底板完全不透明、颜色可调且对比度合格，不遮挡其他工作流或自己的成员节点。

## 16. 需求对齐决策队列

以下问题按顺序逐一确认，每次确认后立即更新本文：

1. 助手悬浮球与窗口采用何种拖动、吸附和位置记忆模型？
2. 空会话顶部保留哪些快捷按钮，哪些只放在输入区？
3. “每个 Markdown 块可复制”的块粒度如何定义？
4. 托管任务目标主要由用户自然语言描述、结构化表单填写，还是二者结合？
5. 托管计划在什么条件下必须人工确认，什么条件下可自动开始？
6. 管理后台的主要使用者是谁，最高频的三个任务是什么？
7. Admin 的四工作域建议是否符合业务，还是需要按其他主线组织？
8. 视觉线框与交互原型确认后，再冻结实现范围和阶段验收清单。
