# RunningHub Workspace And Node Redesign

## 目标

本次设计用于统一收口 RunningHub 在无限画布 2.0 中的后台维护方式、系统并发治理展示方式，以及画布端 RH 节点的用户可见形态。

本轮设计直接解决以下问题：

- RH 工作台虽然已经从 Provider 表单中拆出，但页面结构仍然偏工程态，目录区拥挤、主操作不明确、维护成本高。
- RH 工作台缺少类似 API 设置页的“列表管理 + 详情编辑 + 明确动作按钮”结构，导致工作流和 AI 应用难以新增、修改、保存、删除和测试。
- RH 页目前没有专门的 AI 分析与草案填充能力，仍然主要依赖手工填写。
- 系统页里的 RH 平台并发治理 UI 过于拥挤，与普通任务并发设置混杂，不利于运维人员理解和操作。
- 画布 RH 节点仍暴露 `Webapp ID` / `workflowId` / `runTargetId` 这类后端目录已经掌握的运行标识，节点职责过重，产品形态不稳定。

本轮设计目标：

1. RH 工作台对齐 API 设置页的操作体验和视觉秩序。
2. RH 条目支持明确的新增、保存、删除、启停和测试动作。
3. RH 页补齐“AI 分析并填写结构化草案”的专用能力。
4. 系统页 RH 并发治理区改成独立、清晰、可解释的运维面板。
5. RH 节点去除前端不该暴露的底层运行参数，只保留“选择条目 + 填输入 + 运行”的产品交互。

## 现状判断

### 1. RH 工作台当前问题

当前 RH 工作台已经具备：

- 目录读取
- 工作流 / AI 应用分类切换
- 结构化字段编辑
- 测试运行

但当前页面仍然存在明显问题：

- 左侧目录区布局过空、过高、过挤，信息密度不均匀，列表项停靠在底部，用户视觉焦点不稳定。
- 顶部只有“刷新目录”，没有形成“新增 / 保存 / 删除 / 测试 / 启停”这一组明确的主操作。
- 右侧编辑区是长表单直铺，缺少分组和主次层级。
- 页面整体没有像 API 设置页那样形成“左目录 + 右详情”的稳定操作路径。

### 2. RH 并发治理当前问题

系统页当前 RH 并发治理和图片 / 音频 / 视频并发设置挤在同一区域，说明文案直接夹在输入框旁边，导致：

- 可读性差
- 认知成本高
- 看不出 RH 是独立于普通任务队列之外的平台级窗口

### 3. RH 节点当前问题

当前 RH 节点已经能够：

- 读取后台 catalog
- 选择预设条目
- 拉起运行
- 接收结果

但仍然暴露了过多技术态字段：

- `Webapp ID`
- 实例类型的技术语义过重
- 节点在 UI 上仍像“半个调试器”，而不是“一个稳定的业务节点”

根本问题不是字段有没有用，而是这些字段已经是后端 catalog 的受控数据，不应继续要求画布用户在节点层手工感知和维护。

## 设计原则

### 1. RH 是独立业务域，不是普通 Provider 的附属长表单

RH 仍然挂在 `runninghub` Provider 之下，但工作流 / AI 应用的目录、执行规则和结构化接入，必须以专门的 RH 工作台来承载。

### 2. 后端管理底层标识，前端节点只消费目录条目

前端画布 RH 节点不再直接配置 `webappId / workflowId / runTargetId`。这些运行标识应由后台目录条目和后端执行描述统一管理。

### 3. RH 页要像 API 设置页，而不是像配置 JSON 的开发面板

RH 工作台的目标用户不是只懂接口的工程人员，还包括后续维护目录、修正文档和调试运行的后台操作人员。因此默认入口必须是“列表管理 + 结构化编辑”，不是纯 JSON 文本框。

### 4. AI 助手只输出结构化建议，不直接替代保存

RH 页中的 AI 分析能力要输出结构化草案卡片，而不是散乱文本。管理员在应用前仍然需要人工确认。

## 方案比较

### 方案 A：参考 API 设置页，重构成 RH 专用管理台

特点：

- 左侧目录管理区
- 右侧详情编辑区
- 顶部统一操作条
- 右侧保留后台 AI 助手抽屉

优点：

- 与现有后台操作习惯一致
- 扩展工作流和 AI 应用数量时仍可维护
- 最适合后续继续加 AI 分析、导入、测试和版本治理

缺点：

- 前端和后台结构都需要一轮重构

### 方案 B：保留当前页面，只补按钮和局部样式

优点：

- 改动小

缺点：

- 底层布局问题不会消失
- 后续继续加功能会再次变乱

### 方案 C：拆为 RH Provider 页 + RH 条目页两个后台页面

优点：

- 职责边界最清晰

缺点：

- 当前阶段入口过重
- 操作路径更长

### 结论

本轮采用 **方案 A**。

原因：

- 用户已经明确希望参考 API 设置页布局与设计。
- 当前 RH 工作台后续还要承载 AI 分析、保存、删除、测试、目录筛选和条目维护，继续轻补会很快再次失控。

## RH 工作台重设计

## 页面结构

页面采用三段结构：

1. 顶部 Hero + 操作区
2. 左侧目录管理区
3. 右侧详情编辑区

整体遵循 API 设置页的信息秩序，但不直接复制其表单字段布局。

### 顶部 Hero 区

顶部展示：

- 标题：`RunningHub 工作台`
- 副标题：说明 RH 工作流 / AI 应用从 Provider 大表单拆出，统一在此维护
- 当前 Provider 提示
- 工作流数量
- AI 应用数量

右侧主操作：

- `刷新目录`
- `新建工作流`
- `新建 AI 应用`
- `AI 分析并填写`

说明：

- 新建按钮必须在工作台顶层可见，不再隐藏在局部编辑器里。
- AI 分析并填写是 RH 专用动作，不借用 API 设置页文案。

### 左侧目录区

左侧目录区结构参考 API 设置页左侧平台列表，但针对 RH 做简化：

顶部工具区：

- 搜索框
- 分类切换：
  - `工作流`
  - `AI 应用`
- 状态筛选：
  - `全部`
  - `启用`
  - `停用`

目录列表项显示：

- 条目标题
- 来源 Provider
- 任务能力
- 启用状态
- 输入槽数量

目录项动作：

- 单击选中
- 右侧联动显示详情
- 选中态高亮

目录区底部固定按钮：

- `新增工作流`
- `新增 AI 应用`

关键调整：

- 去掉当前那种“左侧大片空白、列表项压在最下面”的布局。
- 左侧目录区高度自适应、内部独立滚动，视觉上要更接近 API 设置页的平台列表。

### 右侧详情编辑区

右侧采用“头部操作条 + 分组 Section”的结构。

#### 详情头部

展示：

- 条目标题
- 条目类型：工作流 / AI 应用
- Provider 名称
- 启用状态标签
- 最近测试结果标签

头部按钮：

- `保存`
- `另存为`
- `删除`
- `启用/停用`
- `测试运行`

说明：

- 保存按钮必须固定可见。
- 删除按钮必须显式危险态，不藏在其他菜单里。
- 测试运行按钮要成为一等动作，而不是深埋在表单底部。

#### Section 1：基础信息

字段：

- 标题
- 备注
- 类型
- 页面 ID
- 实际运行 ID
- 任务能力
- 缩略图

说明：

- `pageId` 和 `runTargetId` 仍然需要在后台可见，因为后台要做治理和纠错。
- 但这些字段后续不再下放到画布 RH 节点中直接编辑。

#### Section 2：输入槽定义

使用结构化列表编辑器，不默认让用户编辑 JSON。

每个输入槽支持：

- 名称
- nodeId
- fieldName
- 数据类型
- 是否必填
- 单个 / 多个
- 支持连接
- 支持上传
- 支持手工输入

动作：

- 新增输入槽
- 删除输入槽
- 上下排序

#### Section 3：参数 Schema

以结构化编辑器为主，JSON 为高级模式。

字段支持：

- text
- textarea
- number
- boolean
- select
- json

动作：

- 新增参数
- 删除参数
- 调整顺序
- 切换到 JSON 高级编辑

#### Section 4：输出定义

展示并编辑：

- 输出键
- 输出类型
- 单个 / 多个
- 返回路径

动作：

- 新增输出
- 删除输出

#### Section 5：执行规则

分组展示：

- submit 配置
- polling 配置
- 结果提取配置
- 错误提取配置

要求：

- 以结构化字段编辑为主
- JSON 文本框只作为高级视图

#### Section 6：测试与调试

展示：

- 测试 payload
- 请求预览
- 返回预览
- 最近错误

动作：

- `运行测试`
- `复制请求预览`

## RH 专用 AI 分析并填写

## 目标

参考 API 设置页的 AI 协助配置思路，但针对 RH 输出“结构化接入方案”，而不是普通 Provider 的协议猜测结果。

## 入口位置

入口放在 RH 工作台顶部 Hero 操作区，以及右侧详情头部的辅助操作区。

## 输入项

用户可提供：

- RH 页面链接
- workflow / app 页面 ID
- 运行目标 ID
- 文档链接
- 示例请求
- 示例返回
- 备注说明

## 输出结构

AI 输出必须结构化为卡片区：

1. 基础信息草案
2. 输入槽草案
3. 参数 Schema 草案
4. 输出定义草案
5. 执行规则草案
6. 风险提示与待人工确认项

每张卡片支持：

- `应用全部`
- `只应用本卡`
- `插入为新条目`

## 不允许的输出形态

- 纯散文
- 混杂 JSON 和解释文字但无区块边界
- 一次性自动覆盖现有条目

## RH 并发治理区重设计

## 目标

把 RH 并发治理从“和普通任务挤在一排”的输入组，改成系统页里独立、清晰、可解释的配置区。

## 新结构

分为两块：

### 块 1：普通任务并发

采用两行紧凑卡片布局：

- 图片总并发
- 图片单用户并发
- 音频总并发
- 音频单用户并发
- 视频总并发
- 视频单用户并发

### 块 2：RunningHub 平台并发治理

单独一块卡片式区域，展示：

- RH 平台总并发
- 启用 RH 平台并发治理
- 说明文案

说明文案不再挤在输入框旁边，而是独立成一段：

- 普通任务仍先受“类别总并发”和“单用户并发”限制
- RH 任务额外受 RH 平台共享并发窗口限制
- 超过窗口的 RH 任务会自动排队并在窗口释放后递进执行

保存按钮位置：

- 区块右上角或区块底部固定
- 不与文案并排挤压

## RH 节点重设计

## 目标

把 RH 节点从“半配置器”改成“条目驱动的业务节点”。

## 节点保留信息

节点仅保留：

- 条目选择器
- 条目说明
- 输入槽摘要
- 可视化参数区
- 实例类型（仅在条目确实开放该选项时显示）
- 运行按钮
- 状态摘要

## 节点移除字段

从前端 RH 节点移除：

- `Webapp ID`
- `workflowId`
- `runTargetId`
- 手工执行端点

这些参数全部由后台目录条目和后端执行描述统一提供。

## 节点新布局

### 1. 顶部

- 节点标题：`RunningHub`
- 副标题：`工作流` 或 `AI 应用`
- 条目选择器
- 条目说明 / note

### 2. 输入槽摘要区

展示：

- 当前条目的输入槽数量
- 按类型统计：
  - 文本
  - 图片
  - 视频
  - 音频
  - JSON

并显示每类已接入数量。

### 3. 参数区

参数区仅渲染当前条目的可编辑参数，不再展示底层 ID。

### 4. 运行状态区

默认只展示小字摘要：

- `进行中 N`
- `成功 N`
- `失败 N`

如果展开详情，再查看：

- 子任务
- 错误信息
- 最近结果摘要

## 节点运行链路

前端提交只携带：

- 选中的 catalog 条目 ID
- 当前输入槽值
- 当前参数值
- 可选实例类型

后端负责：

- 从 catalog 取 `pageId / workflowId / runTargetId`
- 组装运行 payload
- 执行 RH 上传、提交、轮询和结果提取

## 后端配合要求

后端需提供稳定的 RH 条目执行描述，确保前端节点不再自行维护底层运行标识。

前端 RH 节点后续只依赖：

- catalog 条目
- schema
- execution descriptor

不再依赖节点上手工输入的 `webappId`。

## 迁移要求

### 1. 老 RH 条目

老的 `rhApps / rhWorkflows` 继续兼容读取。

### 2. 老 RH 节点

老节点里如果仍保存了：

- `webappId`
- `rhWorkflowPresetId`
- `appInfo`

则在打开画布时做兼容映射：

- 若能匹配 catalog 条目，则以后端 catalog 为准
- 旧 `webappId` 不再作为主要配置入口展示

### 3. 文档与治理

实施后必须同步更新：

- RH 工作台说明
- RH 节点说明
- 环境同步说明
- 并发治理说明

## 验收标准

### 后台工作台

- RH 工作台能像 API 设置页一样完成条目浏览、切换、保存、删除、启停和测试
- 左侧目录区不再拥挤、空置和失衡
- 新建按钮、保存按钮、删除按钮都清晰可见

### AI 分析

- RH AI 分析输出结构化卡片
- 可局部应用，不是纯文本堆积

### 并发治理

- 系统页 RH 并发治理区可一眼区分“普通任务并发”和“RH 平台并发”

### RH 节点

- 节点不再展示 `Webapp ID`
- 节点仍可运行现有 RH workflow
- 用户只需选择条目和填写业务输入，不需维护底层运行标识

## 结论

本轮 RH 重设计采用：

- 后台 RH 工作台对齐 API 设置页的管理体验
- RH 专用 AI 分析并填写
- 系统页 RH 并发治理独立分区
- 前端 RH 节点去掉底层运行参数暴露

这是当前最适合继续推进的方向，既能解决你现在看到的 UI 混乱和维护困难，也能把 RH 后续扩展成本控制在可持续范围内。
