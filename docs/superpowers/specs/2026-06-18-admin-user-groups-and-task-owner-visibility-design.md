# 后台账号分组与任务发起人展示设计

## 背景

当前后台账号管理能力已经覆盖：

- 创建账号
- 启用/禁用账号
- 角色调整
- 密码重置
- 会话强制下线

但在实际团队协作中，已经出现三个明显缺口：

1. 账号无法归组，导致项目组内账号分发和管理缺少组织结构。
2. 账号缺少可维护备注，运营和测试在后台中难以快速识别“这个账号是谁在用、负责什么、属于哪个场景”。
3. 后台任务列表虽然已经记录 `ownerId`，但界面上看不到任务是由哪个账号发起的，排查问题时必须绕路查人。

同时，现有账号列表缺少删除能力，导致测试账号、临时账号和过期协作账号只能停用，无法完整收束。

因此，本轮需要在不打乱现有权限模型的前提下，补齐：

- 独立的用户组实体
- 账号备注维护
- 账号删除
- 任务列表中的发起账号可视化展示

## 目标

本轮目标：

1. 在后台新增“用户组”管理能力，支持账号按组归属。
2. 为账号增加备注字段，并支持随时修改。
3. 为账号提供安全可控的删除能力。
4. 在后台任务列表中直观看到任务由哪个账号发起，并显示备注信息。
5. 保持现有“角色”和“用户组”职责分离，避免混淆权限模型。

## 非目标

- 不在本轮引入多对多用户组关系。
- 不把用户组直接接入 RBAC 权限判断。
- 不根据用户组自动分配服务商、模型、项目或资源配额。
- 不改动任务归属主逻辑，任务仍然以 `ownerId` 为准。
- 不新增“批量删除账号”。
- 不新增“批量迁移整组账号”的复杂编排功能。

## 方案对比

### 方案 A：在用户表上直接增加 `groupName` 文本字段

做法：

- 用户表直接增加 `groupName`
- 账号编辑时手输组名

优点：

- 改动最少
- 上线最快

缺点：

- 组名无法统一治理，容易出现同义组、多写法、错别字
- 无法独立维护组描述、排序和可视化统计
- 后续做账号分发和筛选时会越来越乱

结论：

- 不采用

### 方案 B：独立用户组实体，每个账号归属一个主组

做法：

- 新增 `用户组` 表
- 用户表增加 `groupId`
- 账号通过下拉选择所属组

优点：

- 结构清晰
- 管理成本低
- 足够覆盖当前“项目组内账号管理与分发”需求
- 后续如需升级为更复杂模型，迁移路径清楚

缺点：

- 一个账号当前只能有一个主组

结论：

- 采用本方案

### 方案 C：独立用户组实体 + 多对多成员关系

做法：

- 新增组表和成员关系表
- 允许一个账号加入多个组

优点：

- 灵活性最高

缺点：

- 首版复杂度明显增加
- 后台交互、筛选口径、任务归属展示都会变重
- 当前需求并未证明“一人多组”是刚需

结论：

- 本轮不采用

## 最终设计

采用方案 B：

- 独立用户组实体
- 每个账号归属一个主组
- 用户备注独立维护
- 任务列表联表展示账号信息

这样既满足项目组管理，又避免把后台做成过重的人事系统。

## 数据结构设计

### 用户组

新增 `用户组` 实体，字段建议如下：

- `id`
- `name`
- `description`
- `sortOrder`
- `createdAt`
- `updatedAt`

设计约束：

- `name` 为后台展示主名称，必须唯一。
- `description` 用于补充说明，例如“灰度测试组”“AIGC 运营组”“项目外包协作组”。
- `sortOrder` 用于后台列表排序，避免全部只能按创建时间排列。

### 用户

在现有用户记录上新增：

- `groupId`
- `remark`

字段职责：

- `groupId`：账号所属主组，可为空。
- `remark`：管理员手工维护的账号说明，不参与登录和权限判断。

说明：

- `role` 仍然只表示权限级别，如 `admin` / `member`。
- `groupId` 只表示组织归属，不承载权限职责。

### 任务列表返回结构

任务记录底层仍保持：

- `ownerId`

但在后台任务列表读取时，补充展示字段：

- `ownerName`
- `ownerEmail`
- `ownerRemark`
- `ownerGroupId`
- `ownerGroupName`
- `ownerDeleted`

说明：

- `ownerDeleted` 用于区分“任务原本有发起人，但该账号后来被删除”的情况。
- 这样前端不需要再次额外查账号，即可直接渲染任务发起人信息。

## 后端模型边界

### 用户组与角色分离

本轮明确：

- 角色决定权限
- 用户组决定组织归属

因此：

- 不能用“组”替代“角色”
- 不能把“是否管理员”挂到组上
- 不能让组逻辑反向影响现有登录和鉴权流程

### 删除账号的保留策略

删除账号时：

- 删除用户记录
- 清理该账号会话
- 保留历史任务
- 保留历史审计日志

任务和审计记录中的账号关联处理：

- 若任务 `ownerId` 采用外键 `on delete set null`，则允许记录继续存在
- 后台列表通过额外快照字段或删除标识展示“历史已删除账号”

本轮要求的结果不是“把历史抹掉”，而是“让历史仍可追溯”。

## 后台界面设计

### 用户与用户组管理页

现有“成员与权限”页扩展为两个工作面：

### 1. 用户组管理区

用于管理组织结构，提供：

- 新建用户组
- 编辑组名
- 编辑组说明
- 调整排序
- 删除用户组
- 查看组内账号数量

删除规则：

- 当组内仍有账号时，不允许直接删除
- 必须先将账号移出或改挂到其他组，再删除该组

这样可以避免“删除组后大量账号变成无组织状态”。

### 2. 账号管理主表

在现有用户表基础上新增列：

- 所属组
- 账号备注

并新增操作：

- 修改备注
- 调整所属组
- 删除账号

保留原有能力：

- 启用/禁用
- 重置密码
- 角色展示

### 3. 账号创建表单

新增账号时建议直接支持：

- 选择所属组
- 填写备注

这样新账号创建后无需再二次补充。

## 任务列表展示设计

任务列表新增“发起账号”列。

推荐展示规则：

- 第一行：优先显示备注；无备注时显示姓名；再无则显示邮箱
- 第二行：邮箱 + 所属组

示例：

- `视频测试账号-A`
- `tester@company.com · 灰度测试组`

特殊状态：

- 若任务发起账号已删除，则显示：
  - 第一行：`已删除账号`
  - 第二行：保留可用的历史标识信息；若无历史快照，则显示 `未知账号`

这样后台人员在排查失败任务、核对来源时，可以直接知道“是谁发起的、属于哪个组、当前账号是否仍存在”。

## 接口设计

### 用户组接口

新增：

- `GET /api/admin/user-groups`
- `POST /api/admin/user-groups`
- `PATCH /api/admin/user-groups/:id`
- `DELETE /api/admin/user-groups/:id`

约束：

- 仅管理员可访问
- 组名唯一
- 删除前检查组内账号数量

### 用户接口

扩展现有：

- `POST /api/admin/users`
- `PATCH /api/admin/users/:id`

新增支持字段：

- `groupId`
- `remark`

新增：

- `DELETE /api/admin/users/:id`

删除约束：

- 不允许删除当前登录账号
- 不允许删除最后一个管理员
- 删除成功后必须撤销会话
- 删除动作必须写审计日志

### 任务列表接口

扩展：

- `GET /api/admin/tasks`

返回中新增：

- `ownerName`
- `ownerEmail`
- `ownerRemark`
- `ownerGroupId`
- `ownerGroupName`
- `ownerDeleted`

后端实现建议：

- Postgres 路径对 `xh_tasks` 和 `xh_users`、`xh_user_groups` 做只读联查
- 文件存储路径在读取时根据当前用户库做映射补全

## 数据规则

### 用户组命名规则

- 同一环境内用户组名称唯一
- 名称用于后台选择器和筛选器展示
- 不允许空白名称

### 备注规则

- 备注允许为空
- 备注仅用于后台管理识别
- 不作为登录凭据、不参与权限判断、不参与任务执行逻辑

### 账号删除规则

删除账号后：

- 当前账号会话应全部失效
- 后续不能再登录
- 历史任务仍保留
- 历史审计仍保留

### 任务发起人展示规则

- 优先展示人类可读信息，而不是裸 `ownerId`
- 备注优先于姓名
- 姓名优先于邮箱
- 组名作为辅助信息展示
- 账号已删除时要显式标记，不允许静默变空

## 审计要求

以下动作必须写入审计日志：

- 创建用户组
- 编辑用户组
- 删除用户组
- 创建账号（含组和备注信息）
- 修改账号备注
- 修改账号所属组
- 删除账号

审计记录至少包含：

- 操作人
- 操作类型
- 目标对象类型
- 目标对象 ID
- 变更摘要
- 请求时间

## 错误处理

### 用户组相关

- 组名重复：返回明确错误，不允许自动覆盖
- 删除非空组：返回“组内仍有账号，无法删除”
- 目标组不存在：更新用户时返回明确错误

### 账号相关

- 删除自己：返回明确错误
- 删除最后一个管理员：返回明确错误
- 更新不存在账号：返回明确错误

### 任务列表相关

- 若账号已删除，任务列表不得报错
- 应正常返回任务，并以“已删除账号”方式展示

## 测试要求

### 用户组管理

至少验证：

1. 可以创建用户组
2. 可以编辑用户组名称和说明
3. 可以删除空用户组
4. 无法删除仍有成员的用户组

### 账号管理

至少验证：

1. 创建账号时可设置所属组和备注
2. 账号列表可修改备注
3. 账号列表可调整所属组
4. 可以删除普通账号
5. 无法删除当前登录账号
6. 无法删除最后一个管理员

### 任务列表

至少验证：

1. 任务列表可显示发起账号信息
2. 备注显示优先级正确
3. 所属组可正常展示
4. 账号删除后历史任务仍可查看
5. 账号删除后任务发起人显示为“已删除账号”或等价明确信息

### 回归测试

至少验证：

1. 原有登录流程不受影响
2. 原有会话管理不受影响
3. 原有任务创建和重试逻辑不受影响
4. 现有角色权限逻辑不受影响

## 风险与控制

### 风险 1：把“角色”和“用户组”混在一起

控制：

- 文案上明确“角色 = 权限，分组 = 组织归属”
- 后端不允许组逻辑进入鉴权判断

### 风险 2：删除账号导致历史任务失去可读性

控制：

- 保留历史任务
- 列表层显式标记“已删除账号”
- 必要时补充展示快照信息

### 风险 3：用户组删除带来脏数据

控制：

- 非空用户组禁止删除
- 用户归组更新前校验 `groupId`

## 完成标准

本轮完成的判断标准：

1. 后台可独立管理用户组。
2. 每个账号可归属一个主组。
3. 每个账号可维护备注。
4. 后台支持安全删除账号。
5. 任务列表能看出任务由哪个账号发起，并显示备注和组信息。
6. 删除账号后，历史任务与审计记录仍可追溯。
