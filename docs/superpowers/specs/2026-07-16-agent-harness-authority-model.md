# Agent / Harness Authority Model

## Status

- Status: proposed for implementation
- Owner: canvas 2.0 integration maintainers
- Date: 2026-07-16

## Problem

Current Agent and Harness governance works when an operator runs the right commands, but current facts have multiple writers:

- product version is repeated across root and workspace package manifests, lock data, generated app version and release documents;
- environment topology is repeated across release scripts, runbooks, ops summaries and root entries;
- deployment state is repeated across Markdown summaries and current release indexes;
- Hook and Harness checks have implementations but no guaranteed activation or durable run evidence;
- recent logbook indexes are manually maintained and can lag behind the latest release.

## Goals

1. Give each mutable operational fact one canonical source.
2. Keep root Agent files short, durable and project-oriented.
3. Make gray and production release commands use the same typed environment interface.
4. Make Harness checks runnable locally, from Git hooks and from CI.
5. Preserve Markdown release/validation/incident records as human audit evidence.
6. Generate or deterministically verify current-state projections and recent indexes.

## Non-goals

- Do not rewrite historical release records.
- Do not move runtime secrets into Git.
- Do not introduce a full task ledger or database.
- Do not change product behavior or provider execution logic.
- Do not remove compatibility aliases in the first rollout.

## Canonical sources

| Fact | Canonical source | Consumers |
| --- | --- | --- |
| Product version | root `package.json` | workspace version sync, build, generated app version |
| Workspace package versions | generated by `scripts/version/set-version.mjs` | package manifests and lockfile |
| Non-secret environment topology | `config/environments.json` | release adapters, runbooks, checks |
| Current deployed state | `ops/current/release-state.json` | current release index, ops summaries, Agent summaries |
| Historical evidence | `docs/logbooks/` | humans, incident/release review |
| Harness policy | `config/harness/*.json` plus scripts | checks, docs projections, CI |

## Design

### Product version

The root `package.json` remains the input. A version command updates all private workspace manifests and internal dependency pins, then runs `npm install --package-lock-only` and the existing release alignment verifier. `packages/shared/src/index.ts` should stop owning a manually edited literal and receive the version through the build contract.

### Environment catalog

`config/environments.json` contains only non-secret values: host, SSH port, remote root, public/internal URLs, service names, shared env path, queue prefix, and expected database name. Secret values stay in server env files.

### Deployment state

`ops/current/release-state.json` contains environment, version, release ID, source commit, deployed timestamp, permission mode, readiness summary, rollback release, and evidence links. A schema validator rejects missing or contradictory fields.

### Documentation projections

`README.md`, `MEMORY.md`, `AGENTS.md`, `docs/prd/README.md`, `ops/current/*.md`, and `docs/memory/*.md` keep navigation and short summaries. They link to the canonical state files and are generated or checked through stable markers. Historical logbooks remain append-only.

### Harness execution and evidence

`scripts/harness/run.mjs` owns the check registry and emits a JSON result with command, status, duration, commit, environment, and artifact paths. The same interface is used by local commands, `.githooks/pre-commit`, and CI. Evidence is runtime output, not a second source of truth for project state.

## Invariants

- No current-state verifier extracts the deployment version from prose.
- `release:verify --env=production` never reads a gray env filename.
- A release cannot be marked current without a matching release record and validation record.
- Every active environment has one entry in `config/environments.json` and `release-state.json`.
- Historical files are never rewritten by generators.

## Acceptance criteria

- `npm run verify:authority-state` passes with zero duplicate current-state writers outside generated projections.
- `npm run release:verify -- --env=gray` and `--env=production` resolve the correct env file and service set.
- `npm run harness:run -- --profile=quick` emits a machine-readable result.
- `npm run setup:codegraph-hooks` followed by `git config --worktree --get core.hooksPath` reports `.githooks`.
- CI invokes the same quick and release contracts.
- `recent-highlights.md` is generated from current dated records and no longer contains stale active version claims.
