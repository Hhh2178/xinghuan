# 权限与业务归属完整性修复执行计划

## 目标

根治权限发布 revision 抖动、用户目录写入触发业务数据级联删除、后台任务未知账号三个关联问题，并建立可验证的灰度与生产恢复路径。

## 执行阶段

1. **线上只读诊断，已完成**
   - 核对任务 owner、任务内嵌 userId、素材 owner 和用户目录关系。
   - 核对用户外键删除策略、用户组创建审计和服务重启时间。
2. **回归测试，已完成**
   - metadata 键顺序变化不增加 Subject revision。
   - 用户组/策略写入不得删除用户、会话、画布、素材或项目。
   - 历史任务可从内嵌 userId 恢复 owner 显示。
   - 任务状态写回不得清空已有 owner。
3. **根因修复，已完成**
   - 用户组与策略改为定点事务写入。
   - 移除 API 运行时 PostgreSQL 全量替换入口。
   - 权限冲突增加最新 revision 反馈、刷新和单次安全重试。
   - 任务列表与用量统计共用稳定 owner SQL 表达式。
4. **本地验证，进行中**
   - 专项 Vitest、全 workspace type-check、lint、构建与 Harness。
   - CodeGraph 同步和变更影响复核。
5. **Gray 验收，待用户另行授权发布**
   - 发布前备份 Gray 数据库并验证恢复清单。
   - 创建测试组、更新策略、移动测试账号，前后比较画布/素材/任务 owner 集合。
   - 并发触发 Subject revision 冲突，确认按钮行内反馈和安全重试。
6. **Production 修复与数据恢复，待单独确认**
   - 先部署阻断数据破坏的代码，再评估历史恢复。
   - 历史任务优先只读显示；画布按孤儿快照候选恢复；素材和项目按备份差异恢复。
   - 禁止用覆盖式导入替代定点恢复。

## 放行条件

- 用户组创建、策略更新、用户换组前后，所有非目标业务表 ID 集合一致。
- Subject reconcile 连续执行两次，第二次注册数为 0 且 revision 不变。
- 管理员任务列表不再把可解析 owner 的任务显示为“未知账号”。
- 全量测试、type-check、lint、build、项目 Harness 和 release Harness 通过。
- Production 发布和历史数据恢复必须分成两个可独立回滚的步骤。
