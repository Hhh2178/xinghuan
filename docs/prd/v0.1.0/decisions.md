# v0.1.0 Decisions

## D-001 放弃旧 Node Banana 改造路线

日期：2026-06-04

背景：

旧项目在节点数量、节点扩展、模型后台、执行链路和云端项目等方面出现结构性不匹配。继续修补会让功能入口、后端能力和用户体验持续脱节。

备选方案：

- 继续在旧项目上修补。
- 从旧项目某个标签回退后重构。
- 启动无限画布 2.0 新项目。

结论：

启动无限画布 2.0 新项目。旧项目只作为经验和需求来源，不作为主干继续开发。

影响：

- 后续开发不再以 `node-banana-enterprise` 为默认工作目录。
- 旧项目中已完成的 Provider、worker、后台等能力只可经评估后迁移思想，不直接假设可复用代码。

复查条件：

- 若新基底 POC 无法满足节点扩展和任务系统要求，需要重新评估自研核心画布。

## D-002 不采用一个服务商一个节点

日期：2026-06-04

背景：

旧项目中用户找不到 GRSAI 节点，说明“节点、模型、服务商”概念没有清晰分层。若每个服务商都做一个节点，后续模型数量增长会导致节点爆炸。

结论：

采用通用生成节点。Provider 和模型在后台管理，节点内选择具体服务商和模型，参数与输入端口由 schema 驱动。

影响：

- 图像、视频、文本、音频节点都需要模型目录支持。
- 后台 schema 能力必须优先于堆节点数量。

## D-003 后台必须独立 Web 化

日期：2026-06-04

背景：

旧项目将管理能力挂在画布侧边，造成工作台和后台职责混杂。

结论：

2.0 后台必须是独立页面或独立应用，只有管理员和开发者可访问。

影响：

- 画布只保留创作相关设置。
- Provider、模型、用户、任务、日志和系统设置进入后台。

## D-004 云端项目是默认主存储

日期：2026-06-04

背景：

本地文件夹保存不适合公司多人内部 Web 系统，也不利于用户隔离和服务器部署。

结论：

项目、画布、工作流和素材默认保存到云端服务器。本地文件只作为备份导入导出。

影响：

- v0.1.0 数据模型必须包含用户、项目、画布、工作流、素材和任务。

## D-005 服务商配置只保留在统一后台

日期：2026-06-05

背景：

T8 画布前端仍保留 API/服务商设置入口，容易让创作工作台继续承担 Key、Base URL、模型列表等后台职责。用户明确要求沿用 T8 成熟画板 UI，但服务商配置、模型拉取和模型选择必须由统一后台调控。

备选方案：

- 保留画布前端 API 设置入口，后台只做同步展示。
- 画布和后台都能编辑 Provider。
- 移除画布入口，Provider 和模型目录只由后台管理。

结论：

移除画布前端 API/服务商设置入口。Provider、Key、Base URL、验证地址、模型拉取、选择导入、模型分类和手工维护全部进入统一后台。画布只消费后台已启用的语言、图像、视频三类模型。

影响：

- 画布顶部不再展示 `API 设置` 齿轮入口。
- 后台 Provider 管理必须从简单表格升级为完整服务商编辑器。
- 模型目录必须按 `chat`、`image`、`video` 三类维护。
- Worker 和通用节点后续只能通过后台模型目录读取可用模型。

复查条件：

- 当画布通用节点完全切换到后台模型消费接口后，清理迁移期保留的旧 T8 API settings store 兼容加载。

## D-006 Phase 3 先做任务输出素材闭环，再谈生产切换

日期：2026-06-06

背景：

Phase 2 已经把后台模型治理、三类通用节点、真实代理调用和 `grsai_draw` Worker Adapter 跑通，但当前任务成功后的结果仍主要停留在任务 `result` 和 OutputNode 临时下载层，尚未形成“任务 -> 输出素材记录 -> 素材空间 -> 项目/画布归属”的完整沉淀链路。与此同时，灰度已经出现过后台说明不够直观、输出节点预览高度不收口和管理员凭据状态漂移等收口问题，说明不能再按“灰度能生成就可以切生产”的标准推进。

备选方案：

- 直接以当前灰度 release 为基线准备 `canvas.hhh2121.xyz` 生产切换。
- 继续扩展更多厂商或更多节点，再回头补任务和素材闭环。
- 先进入 Phase 3，优先补齐输出素材落库、素材空间联动、取消/重试和生产预检收口。

结论：

采用第三种方案。先做 Phase 3 闭环，生产切换顺延到 Phase 3 灰度验收之后。

影响：

- 计划书需要从“Phase 2 后准备生产切换”改为“Phase 3 先落库和联动，再做生产预检”。
- 当前最高优先级从继续扩厂商/扩节点切换为 Worker 输出写入输出素材与资源库。
- 生产预检文档只能以最新灰度 release 和最新收口状态为基线，不能继续引用旧 release。

复查条件：

- 当任务成功、失败、取消、重试都能追踪，且输出素材能在项目素材空间稳定查看后，再重新评估生产切换窗口。

## D-007 暂缓 RunningHub 真实工作流测试，先推进生产预检

日期：2026-06-07

背景：

RunningHub 工作流字段映射、目录接口和画布预设消费第一版已经进入灰度，`verify:runninghub-workflow-contract` 与 `verify:runninghub-workflow-api` 均已通过。但灰度后台当前还没有已启用的真实 RunningHub 工作流卡片，因此目录结果为空。与此同时，用户已明确要求“暂时先不做这个 RH 的测试”，并希望先继续推进下一步工作。

备选方案：

- 继续补录真实 RunningHub 工作流卡片，并马上做字段展开和预览运行验收。
- 维持当前第一版灰度实现，记录目录为空和测试暂缓的现状，先推进生产预检与切换准备。
- 回退 RunningHub 第一版灰度实现，等未来再重做。

结论：

采用第二种方案。当前保留 RunningHub 目录/字段映射第一版在灰度，不继续做真实工作流卡片录入、字段展开和预览运行类测试；本轮推进重心切到生产预检和非 RH 阻塞项收口。

影响：

- 文档、预检和 release 结论都要明确写明“RH 真实测试暂缓”。
- 生产切换准备基线继续使用当前灰度 release `20260607-0218-phase3-runninghub-workflow-gray`，但不能把 RH 真实工作流能力视为已完成正式验收。
- 若后续恢复 RH 真实测试，需要先在灰度后台补入真实工作流卡片，再补画布字段展开和预览运行验收。

复查条件：

- 当用户恢复该事项，且灰度后台已具备至少一条可用 RunningHub 工作流卡片时，重新进入真实工作流验收。

## D-008 入口 UI 设计文件只作为视觉 brief 来源，不直接逐像素照搬

日期：2026-06-07

背景：

用户提供了 `stitch_ui_optimization_and_transitions` UI 设计文件，其中包含 `_1` 过渡页 HTML、`_2` 登录页 HTML/截图和 `stellar_canvas_internal/DESIGN.md`。该文件包提供了星幻画布入口页需要的深空色板、青绿/青蓝强调色、磨玻璃卡片、鼠标跟随光场和短暂过渡动画方向，但同时也包含不适合正式产品的演示元素：外链图片、中心 logo、白色输入框、SSO/组织网络占位、坐标/延迟调试文字、Alpha 页脚和白闪爆发。

备选方案：

- 直接把设计稿 HTML/CSS 复制进现有 React 项目。
- 完全放弃该设计稿，重新从零写视觉方案。
- 提取其中可用的视觉语言，写成 Google/Gemini 前端实现 brief，并明确禁用项。

结论：

采用第三种方案。`entry-ui-google-brief.md` 作为后续 Google/Gemini 前端生成和人工落地的权威入口 UI brief；设计稿只作为参考源，不直接进入生产代码。后续实现必须保持现有登录业务逻辑、认证 API、默认账号预填和错误处理不变。

影响：

- 后续入口页应采用左侧轻量伪 3D 微缩星系星图、右侧磨玻璃登录卡片的横向构图。
- 输入框必须使用深色嵌入式背景，不能采用设计稿截图里的白色输入框。
- 过渡动画应替换旧 T8/旧项目页面，但不能使用固定长等待、中心 logo、调试信息或纯白闪屏。
- 不得依赖 Tailwind CDN、Google Fonts CDN、远程图片 URL 或任何会破坏离线/部署稳定性的外链资源。

复查条件：

- 当 Google/Gemini 产出新前端代码后，必须按 brief 检查左侧无文字/无 logo、深色输入框、鼠标跟随克制、reduced-motion 兜底、登录 API 不变、移动端无横向滚动，并通过 Web type-check/build 与入口 UI 验证脚本。

## D-009 Provider 接入采用“结构化默认配置 + 受控高级配置 + 专用 Adapter”三层方案

日期：2026-06-08

背景：

当前后台模型治理已经支持 `protocol`、`inputProfile` 和 `parameterSchema`，但在接入更多视频模型时暴露出两类缺口：一是部分上游并不走“同步返回结果”的 OpenAI-like 代理，例如 APIMart 视频模型会先返回 `task_id` 再通过 `/v1/tasks/{task_id}` 轮询；二是当前前端和后台仍主要依赖字符串型 `inputProfile` 推断视频节点是否支持多参考图、首帧和尾帧，这不足以稳定支撑多 Provider 扩展。

备选方案：

- 继续以当前 `inputProfile + 通用同步代理` 为主，遇到差异时逐个补临时分支。
- 对每个特殊服务商单独做一套完全独立的节点和配置界面。
- 保留统一节点与统一后台，但将模型接入升级为“结构化默认配置 + 受控高级配置 + 专用 Adapter”三层方案。

结论：

采用第三种方案。大多数模型继续走统一后台和统一节点，但模型元数据需要补充结构化 `inputCapabilities`，特殊字段差异通过受控 `advancedConfig` 表达，协议差异明显的 Provider 通过专用 adapter 接入。

影响：

- 后台模型编辑需要新增视频输入能力开关，至少覆盖“多参考图 / 首帧 / 尾帧”。
- 画布视频节点切换模型后，需要按后台能力动态展示对应输入口。
- `inputProfile` 保留为兼容字段，但不再作为长期唯一真相源。
- APIMart 这类异步视频协议不能继续硬塞进当前同步视频代理，需要 adapter 化处理提交、轮询和结果提取。
- APIMart `gpt-image-2` 这类异步图像协议也不能继续按同步 `/images/generations` 结果处理；图像代理必须支持 `task_id` -> `/v1/tasks/{task_id}` 的轮询闭环。
- 已跑通的 GRSAI 链路继续保留，但其意义调整为“已接入样本”，不再代表平台已经具备通用多 Provider 扩展框架。

复查条件：

- 当结构化 `inputCapabilities`、后台能力开关、视频节点动态输入和至少一条异步视频 adapter 全部落地后，再评估是否继续抽象更多协议层或收缩高级配置范围。

## D-010 AI 助手采用“产品层自有 + 项目专属 Hermes runtime”方案

日期：2026-06-08

背景：

无限画布已经具备统一后台、Provider / 模型管理、任务队列、灰度 / 生产双入口和外部 API 接入框架。后续希望新增两类 AI 助手能力：一类面向画布用户做创作辅助，一类面向管理员做 Provider 接入分析、配置草案、API 联网测试和状态审计。同时必须控制权限边界，避免助手直接危及站点或生产环境。

备选方案：

- 直接把当前服务器正在运行的共享 Hermes 实例接入无限画布。
- 在无限画布项目中完全自建一套独立智能体平台，不复用 Hermes。
- 产品层在无限画布项目内自建，执行层做成可替换接口，当前阶段接入项目专属隔离的 Hermes runtime。

结论：

采用第三种方案。前端做轻量创作副驾驶，后台做安全审计 / 配置工作台；Hermes 只作为项目专属隔离执行内核接入，不直接替代项目产品层和管理层。

影响：

- 需要建立前端创作助手、后台审计 / 配置助手、助手编排层、受控工具层和项目专属 Hermes runtime 的分层结构。
- 后台助手第一阶段只做“分析 + 草案生成 + 人工确认后应用”，不直接写生产密钥、不直接部署、不直接改核心系统配置。
- Hermes 必须通过工具白名单访问画布上下文、Provider / 模型目录、任务状态和安全联网测试接口，不得直接获得任意 shell、任意数据库直写或任意部署权限。
- 前端助手采用“悬浮面板 + 可固定侧栏”形态，参考 Jaaz 的副驾驶式交互，但适配当前企业型画布。
- 后续实现和验收以 `assistant-hermes-plan.md` 与 `assistant-hermes-implementation-plan.md` 为主线。

复查条件：

- 当后台助手最小工作台、项目专属 Hermes runtime、前端助手最小交互壳和草案审批闭环全部完成灰度验收后，再评估是否继续增强自动化能力或拆分双 runtime。
