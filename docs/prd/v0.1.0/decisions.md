# v0.1.0 Decisions

## D-001 放弃旧 Node Banana 改造路线

日期：2026-06-04

背景：

旧项目在节点数量、节点扩展、模型后台、执行链路和云端项目等方面出现结构性不匹配。继续修补会让功能入口、后端能力和用户体验持续脱节。

备选方案：

- 继续在旧项目上修补。
- 从旧项目某个标签回退后重构。
- 启动无限画布 2.0 新项目。

结论：

启动无限画布 2.0 新项目。旧项目只作为经验和需求来源，不作为主干继续开发。

影响：

- 后续开发不再以 `node-banana-enterprise` 为默认工作目录。
- 旧项目中已完成的 Provider、worker、后台等能力只可经评估后迁移思想，不直接假设可复用代码。

复查条件：

- 若新基底 POC 无法满足节点扩展和任务系统要求，需要重新评估自研核心画布。

## D-002 不采用一个服务商一个节点

日期：2026-06-04

背景：

旧项目中用户找不到 GRSAI 节点，说明“节点、模型、服务商”概念没有清晰分层。若每个服务商都做一个节点，后续模型数量增长会导致节点爆炸。

结论：

采用通用生成节点。Provider 和模型在后台管理，节点内选择具体服务商和模型，参数与输入端口由 schema 驱动。

影响：

- 图像、视频、文本、音频节点都需要模型目录支持。
- 后台 schema 能力必须优先于堆节点数量。

## D-003 后台必须独立 Web 化

日期：2026-06-04

背景：

旧项目将管理能力挂在画布侧边，造成工作台和后台职责混杂。

结论：

2.0 后台必须是独立页面或独立应用，只有管理员和开发者可访问。

影响：

- 画布只保留创作相关设置。
- Provider、模型、用户、任务、日志和系统设置进入后台。

## D-004 云端项目是默认主存储

日期：2026-06-04

背景：

本地文件夹保存不适合公司多人内部 Web 系统，也不利于用户隔离和服务器部署。

结论：

项目、画布、工作流和素材默认保存到云端服务器。本地文件只作为备份导入导出。

影响：

- v0.1.0 数据模型必须包含用户、项目、画布、工作流、素材和任务。

## D-005 服务商配置只保留在统一后台

日期：2026-06-05

背景：

T8 画布前端仍保留 API/服务商设置入口，容易让创作工作台继续承担 Key、Base URL、模型列表等后台职责。用户明确要求沿用 T8 成熟画板 UI，但服务商配置、模型拉取和模型选择必须由统一后台调控。

备选方案：

- 保留画布前端 API 设置入口，后台只做同步展示。
- 画布和后台都能编辑 Provider。
- 移除画布入口，Provider 和模型目录只由后台管理。

结论：

移除画布前端 API/服务商设置入口。Provider、Key、Base URL、验证地址、模型拉取、选择导入、模型分类和手工维护全部进入统一后台。画布只消费后台已启用的语言、图像、视频三类模型。

影响：

- 画布顶部不再展示 `API 设置` 齿轮入口。
- 后台 Provider 管理必须从简单表格升级为完整服务商编辑器。
- 模型目录必须按 `chat`、`image`、`video` 三类维护。
- Worker 和通用节点后续只能通过后台模型目录读取可用模型。

复查条件：

- 当画布通用节点完全切换到后台模型消费接口后，清理迁移期保留的旧 T8 API settings store 兼容加载。

## D-006 Phase 3 先做任务输出素材闭环，再谈生产切换

日期：2026-06-06

背景：

Phase 2 已经把后台模型治理、三类通用节点、真实代理调用和 `grsai_draw` Worker Adapter 跑通，但当前任务成功后的结果仍主要停留在任务 `result` 和 OutputNode 临时下载层，尚未形成“任务 -> 输出素材记录 -> 素材空间 -> 项目/画布归属”的完整沉淀链路。与此同时，灰度已经出现过后台说明不够直观、输出节点预览高度不收口和管理员凭据状态漂移等收口问题，说明不能再按“灰度能生成就可以切生产”的标准推进。

备选方案：

- 直接以当前灰度 release 为基线准备 `canvas.hhh2121.xyz` 生产切换。
- 继续扩展更多厂商或更多节点，再回头补任务和素材闭环。
- 先进入 Phase 3，优先补齐输出素材落库、素材空间联动、取消/重试和生产预检收口。

结论：

采用第三种方案。先做 Phase 3 闭环，生产切换顺延到 Phase 3 灰度验收之后。

影响：

- 计划书需要从“Phase 2 后准备生产切换”改为“Phase 3 先落库和联动，再做生产预检”。
- 当前最高优先级从继续扩厂商/扩节点切换为 Worker 输出写入输出素材与资源库。
- 生产预检文档只能以最新灰度 release 和最新收口状态为基线，不能继续引用旧 release。

复查条件：

- 当任务成功、失败、取消、重试都能追踪，且输出素材能在项目素材空间稳定查看后，再重新评估生产切换窗口。

## D-007 暂缓 RunningHub 真实工作流测试，先推进生产预检

日期：2026-06-07

背景：

RunningHub 工作流字段映射、目录接口和画布预设消费第一版已经进入灰度，`verify:runninghub-workflow-contract` 与 `verify:runninghub-workflow-api` 均已通过。但灰度后台当前还没有已启用的真实 RunningHub 工作流卡片，因此目录结果为空。与此同时，用户已明确要求“暂时先不做这个 RH 的测试”，并希望先继续推进下一步工作。

备选方案：

- 继续补录真实 RunningHub 工作流卡片，并马上做字段展开和预览运行验收。
- 维持当前第一版灰度实现，记录目录为空和测试暂缓的现状，先推进生产预检与切换准备。
- 回退 RunningHub 第一版灰度实现，等未来再重做。

结论：

采用第二种方案。当前保留 RunningHub 目录/字段映射第一版在灰度，不继续做真实工作流卡片录入、字段展开和预览运行类测试；本轮推进重心切到生产预检和非 RH 阻塞项收口。

影响：

- 文档、预检和 release 结论都要明确写明“RH 真实测试暂缓”。
- 生产切换准备基线继续使用当前灰度 release `20260607-0218-phase3-runninghub-workflow-gray`，但不能把 RH 真实工作流能力视为已完成正式验收。
- 若后续恢复 RH 真实测试，需要先在灰度后台补入真实工作流卡片，再补画布字段展开和预览运行验收。

复查条件：

- 当用户恢复该事项，且灰度后台已具备至少一条可用 RunningHub 工作流卡片时，重新进入真实工作流验收。
