# 正式环境多用户加固推进方案（2026-06-13）

## 背景

本轮生产级代码审查已经确认，当前项目虽然能构建、能部署、能完成基础生成链路，但距离“正式上线的多用户服务器端项目”仍有明显差距。核心风险不是单点功能缺失，而是数据归属、并发覆盖、状态一致性和运维可追溯性还没有完全收口。

本方案用于把后续修复从“发现一个问题修一个问题”切换为“按正式多用户标准分阶段治理”。

## 目标

- 消除跨用户数据接管和误覆盖风险。
- 把 PostgreSQL 模式从“单机文件思维迁移版”收口为“面向并发写入的正式仓储实现”。
- 建立灰度到正式可复用的上线门槛，避免再次出现“代码已更新但用户数据异常”的情况。
- 为后续团队协作、配额、审计、任务扩容和计费治理预留稳定底座。

## 当前确认的高风险问题

### P0

- 画布写入存在基于客户端 `id` 的跨用户接管风险。
- `AuthDb` / `AdminDb` 的 PostgreSQL 写入仍保留整表删除后重写模式。

### P1

- 画布列表和资源库仍然采用“按当前客户端视图整体替换”的写法。
- 会话安全不足，缺少 CSRF、登录限流、会话元数据与会话治理。
- 任务取消不是端到端取消，只停止本地轮询。

### P2

- 审计、日志、请求链路、任务追踪信息不足。
- 后台任务/审计/素材读取缺少分页和索引收口。
- 正式环境下的回归验收缺少并发、竞态和数据保全门槛。

## 实施边界

### 允许做的事

- 新增数据库迁移、索引、版本字段、约束和更细粒度的仓储方法。
- 拆分 `read*Db / write*Db` 这种整库读写模型，改成按实体更新。
- 补充灰度和正式验收脚本、回归脚本、审计字段和运维文档。
- 为前端保存协议增加 `revision` / `version` / `etag` 一类并发控制字段。

### 禁止做的事

- 禁止再新增任何“先全删再全量写回”的 PostgreSQL 仓储逻辑。
- 禁止任何依赖客户端传入 `id` 即可改变 `owner_id` 的写入路径继续上线。
- 禁止在未完成灰度并发验收前，将本轮仓储重构直接推正式。
- 禁止以“空列表替换”“整库同步”“导入覆盖”作为正式环境默认保存策略。
- 禁止在没有备份快照和回滚说明的情况下执行影响 `xh_canvases`、`xh_assets`、`xh_tasks`、`xh_sessions` 的迁移。
- 禁止把“前端显示取消”继续视为“上游任务已真正取消”。

## 方案总览

## Phase A - 数据归属与仓储止血

目标:

- 先把最危险的数据归属和整表覆盖风险停掉。

实施项:

- 画布写入改为“仅允许当前 owner 更新自己的记录”。
- 去掉 `xh_canvases` 写入中的 `owner_id = excluded.owner_id` 模式。
- `PUT /api/canvas/:id` 和 `POST /api/canvas/:id/auto-save` 必须区分“新建画布”和“更新已有画布”。
- 新建只能由 `/api/canvas` 创建流程产生。
- 更新必须要求 `id + owner_id` 匹配成功，否则返回明确的所有权错误。
- `writeAuthDbPostgres` 不再 `delete from xh_sessions` / `delete from xh_users` 后全量回灌。
- `writeAdminDbPostgres` 不再 `delete from xh_providers/xh_models/xh_tasks/xh_audit_logs/...` 后整库回灌。
- 资源库保存改为增量 upsert / delete，而不是删光当前用户全部素材后重建。
- 画布列表保存改为单画布元数据更新，不再把客户端列表当作服务器唯一真相。

交付物:

- 新迁移文件。
- 重构后的 API 仓储函数。
- 覆盖跨用户写入和并发覆盖的验证脚本。

## Phase B - 并发控制与版本化保存

目标:

- 解决多标签页、多设备、旧缓存和慢请求导致的新旧数据互相覆盖。

实施项:

- 为画布、资源库、后台关键配置增加 `revision` 或 `version` 字段。
- 前端保存请求附带“当前编辑基线版本”。
- 后端写入时执行乐观锁校验。
- 发生版本冲突时返回明确错误，不再静默覆盖。
- 后台 Provider / Model / Assistant Settings / Task Queue Settings 也采用实体级版本更新。
- 新增“服务器返回最新版本，前端决定合并/重载”的冲突处理协议。

交付物:

- 数据库迁移。
- 前后端保存协议更新。
- 版本冲突回归测试。

## Phase C - 会话与权限安全加固

目标:

- 把当前“可用”会话机制提升到公网正式服务最低安全线。

实施项:

- 对写操作加入 CSRF 校验。
- 对登录接口加入 IP + 账号维度的限流与失败计数。
- `xh_sessions` 增加 `last_seen_at`、`ip`、`user_agent`、`revoked_at` 等元数据。
- 后台增加会话查看与强制下线能力。
- 审计日志写入请求来源信息，不再只记动作摘要。

交付物:

- 会话表迁移。
- 鉴权中间层更新。
- 管理后台会话治理入口。

## Phase D - 任务状态机与取消闭环

目标:

- 让任务状态真实反映上游状态，减少“界面显示完成/取消，但上游实际仍在跑”的偏差。

实施项:

- 为各类 Provider 明确声明是否支持 upstream cancel。
- 取消接口按 Provider 协议执行真实取消，至少把“不支持上游取消”与“已确认上游取消”分开。
- 为异步任务增加 reconciliation / reaper 机制。
- 对长时间 `running` / `queued` 但无日志推进的任务做自动复查。
- 管理后台任务列表改为分页查询，不再全量返回全部任务。

交付物:

- Provider cancel contract。
- Worker / API 任务补偿逻辑。
- 任务分页和索引优化。

## Phase E - 可观测性与上线门槛

目标:

- 建立正式环境定位问题的基本能力。

实施项:

- API 和 Worker 统一输出 `requestId`、`taskId`、`userId`、`providerId`、`modelId`。
- 审计日志补齐 `ip`、`user_agent`、`request_id`。
- 后台系统页补充数据库目标、队列积压、失败任务趋势、最近冲突写入统计。
- 灰度和正式上线前必须完成并发验收、脏数据回归和回滚演练。

交付物:

- 日志字段标准。
- 运维验收清单。
- 回滚判定门槛。

## 优先级与执行顺序

1. Phase A
2. Phase B
3. Phase C
4. Phase D
5. Phase E

说明:

- Phase A 和 Phase B 完成前，不建议继续扩大正式环境用户规模。
- Phase C 之前，不建议把当前登录体系暴露给更大范围公网用户。
- Phase D 完成前，任务取消、失败原因和成本统计都不适合当作正式 SLA 承诺。

## 每阶段完成标准

### Phase A 完成标准

- 不存在任何整表删除后回写的 PostgreSQL 核心仓储路径。
- 画布不能通过伪造 `id` 改变 `owner_id`。
- 旧的“空列表 / 旧列表覆盖”路径不再影响服务器端真实数据集。

### Phase B 完成标准

- 多标签页并发保存会返回明确冲突，不会静默吞掉新数据。
- 后台关键设置支持版本化更新。

当前状态（2026-06-13）:

- 已完成并通过灰度真实验收：
  - 画布 revision 冲突保护
  - 资源库 revision 冲突保护
  - 后台 AI 助手配置 revision 冲突保护
  - 后台任务并发配置 revision 冲突保护

### Phase C 完成标准

- 写操作具备 CSRF 防护。
- 登录具备基础限流。
- 后台能查看和撤销会话。

### Phase D 完成标准

- 取消结果能明确区分本地取消与上游取消。
- 长时间悬挂任务能自动复核。
- 后台任务查询改为分页。

### Phase E 完成标准

- 关键链路日志可串联到具体用户、任务和请求。
- 灰度和正式都有固定上线门槛文档和回滚演练记录。

## 风险提示

- 本轮仓储改造会触碰画布、用户、任务、后台配置四条核心链路，必须分阶段推进。
- 仅靠前端修补无法解决当前问题，必须先收口服务端写入模型。
- 任何“为兼容旧逻辑保留全量覆盖入口”的做法，都会把风险继续带到正式环境。

## 与后续实施的接口约定

- 后续具体开发任务必须以本方案的 `Phase` 为单位拆单。
- 每个 Phase 都要有独立灰度验收记录。
- 每个 Phase 完成后都要同步更新：
  - `DEVLOG.md`
  - `MEMORY.md`
  - `ops/README.md`
