## 分项判断

### 1. `releases/`

- 当前最大占用目录，约 `2.78 GB`。
- 其中单个 `20260608-204728-audit-fixes-gray.tar.gz` 已超过 `1.2 GB`。
- 这些文件大多属于历史灰度/发布打包产物，不是项目本体源码。

建议：

- 后续如确认某个历史包已不再作为当前值守或回滚证据，可按“单文件明确路径”原则逐个清理。
- 保留中的包体应在 `ops/` 或归档索引里说明用途，避免目录里只剩文件名、没有保留理由。

### 2. `development/`

- 约 `455.89 MB`，其中几乎全部来自 `development/_archive/`（`478,006,419 bytes`）。
- 说明当前不是活跃方案过多，而是过程归档已明显大于活跃资料。

建议：

- 后续继续保留 `development/README.md` 作为索引。
- 如果归档继续增长，优先补索引和批次说明，而不是让 `_archive/` 变成无目录说明的黑箱。

### 3. `dist-release/`

- 约 `424.84 MB`。
- 当前为多批 release 打包输出，单文件多在 `5.2-6.1 MB` 左右，数量积累后占用明显。

建议：

- 只保留当前 gray/prod 基线和确有审计意义的少量包体。
- 其余历史分发包如果已经被 `releases/` 中更完整的归档替代，可后续逐个评估。

### 4. `output/`

- 约 `180.31 MB`，主要来自 `output/playwright/`（`175,630,698 bytes`）。
- 这是自动化验收截图、浏览器产物和临时证据，不属于长期源码资产。

建议：

- 长期保留“结论”到 `ops/` / `docs/` / `DEVLOG.md`。
- 原始截图和浏览器中间产物只在仍需复盘时保留，后续按单文件逐个处理。

### 5. `.codegraph/`

- 当前约 `56.35 MB`，与 `codegraph status` 输出一致。
- 这是合理的本机索引成本，不应被误判为源码膨胀。

建议：

- 保持 `.gitignore` 忽略。
- 通过 hook 自动 `sync`，避免索引长期滞后。

## 当前治理结论

- 从“项目文件是否过多”的角度看：
  - 源码和长期文档并不夸张。
  - 真正过多的是本机产物、历史包体和过程归档。
- 因此治理重点不应放在压缩源码结构，而应放在：
  1. 建立清楚的保留理由
  2. 保持归档索引
  3. 在不触碰当前值守证据的前提下，按单文件路径逐步瘦身

## 后续瘦身顺序

建议按以下顺序排查：

1. `releases/` 中不再承担回滚/审计职责的超大历史包
2. `dist-release/` 中被当前基线覆盖的旧分发包
3. `output/playwright/` 中已沉淀结论后的原始截图/浏览器产物
4. `development/_archive/` 中缺少索引说明的历史过程资料
5. 仅在确有必要时重建 `.codegraph/`，不把它当作第一优先级清理对象

## 管理规则

- 不允许批量删除目录或递归清空。
- 如果后续确实要清理，只能对单个明确路径文件执行逐个删除。
- 每轮清理前先更新保留理由或归档索引，避免“删完以后不知道为何删、留着的人也不知道为何留”。
