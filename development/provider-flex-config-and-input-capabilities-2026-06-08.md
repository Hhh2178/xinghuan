# Provider 灵活配置与输入能力开关方案备忘

状态：候选方案已确认，待进入正式实现

日期：2026-06-08

## 背景

当前后台 Provider/模型目录已经可以管理基础协议、模型分类、`inputProfile` 和参数 schema，但在接入不同视频服务商时暴露出两个问题：

1. 统一视频代理默认按“同步返回视频 URL”的 OpenAI-like 方式处理，遇到 APIMart 这类“先提交任务，再轮询状态”的异步视频协议时会失败。
2. 模型输入能力目前仍主要依赖字符串型 `inputProfile`，不足以精确表达“多参考图 / 首帧 / 首尾帧 / 特殊字段映射”等差异。

用户已确认采用一套分层方案，让平台既保留默认统一配置，又能为特殊模型提供更宽松但受控的扩展空间。

## 方案结论

采用三层模型接入架构：

### 第一层：默认结构化配置

适用于大多数 OpenAI-like / 常规图像、视频、LLM 模型。

核心目标：

- 后台优先使用结构化字段描述模型能力，而不是只靠自由文本。
- 画布节点优先读取结构化能力决定展示哪些输入口、参数项和说明。
- 常规模型无需写额外适配代码即可接入。

建议新增或强化的模型字段：

- `inputCapabilities`
  - `prompt`
  - `imageReference`
  - `multiImage`
  - `firstFrame`
  - `lastFrame`
  - `mask`
  - `audioReference`
- `parameterSchema`
- `durationOptions`
- `resolutionOptions`
- `aspectRatioOptions`

其中视频模型首批重点落地：

- 是否支持多参考图
- 是否支持首帧
- 是否支持尾帧
- 是否允许首尾帧同时传入

### 第二层：宽松高级配置

适用于“协议大体相近，但字段名、枚举值、请求体结构略有差异”的模型。

核心目标：

- 不为了每一个字段差异都硬编码新分支。
- 管理员可以在后台为单个模型填写受控的高级配置。
- 高级配置只影响该模型，不污染通用节点逻辑。

建议高级配置范围：

- 请求字段映射
  - 例如 `resolution -> size`
  - `referenceImages -> image_urls`
- 固定附加字段
  - 例如 `quality: "720p"`
- 响应路径提示
  - 例如最终视频位于 `result.videos`
- 任务状态字段提示
  - 例如 `status`、`task_id`
- 轮询参数
  - 例如轮询间隔、超时上限

约束：

- 高级配置仍使用白名单字段，不直接允许任意脚本执行。
- 后台需要提供 JSON 校验和示例模板，避免管理员随意写出不可维护结构。

### 第三层：协议 Adapter

适用于与默认链路差异明显的 Provider/模型。

触发条件：

- 提交接口与结果接口完全分离
- 状态机明显不同
- 请求/响应字段重映射过多
- 需要任务轮询、分阶段解析或额外签名逻辑

典型案例：

- APIMart `grok-imagine-1.5-video-apimart`
  - 提交：`POST /v1/videos/generations`
  - 返回：`task_id`
  - 轮询：`GET /v1/tasks/{task_id}`
  - 终态视频：`result.videos`

这类模型不应继续硬塞进当前“同步视频 URL”代理分支，而应由专门的视频 adapter 处理。

## 后台与画布设计要求

### 后台

视频模型编辑区新增显式能力开关：

- 多参考图
- 首帧
- 尾帧

配套原则：

- 保留现有 `inputProfile` 作为兼容字段，但不再作为长期唯一真相源。
- 后台保存时同步维护结构化 `inputCapabilities`。
- 提供“默认结构化配置”和“高级配置 JSON”两个层次，避免普通接入和特殊接入混在一起。

### 画布视频节点

视频节点切换后台模型后，按模型能力动态展示输入区域：

- 开启多参考图：显示多图参考输入
- 开启首帧：显示首帧输入
- 开启尾帧：显示尾帧输入
- 若仅支持首帧，不显示尾帧
- 若仅支持多图，不强行展示首尾帧

节点不再把“首帧/尾帧一定存在”写死在前端逻辑里。

## 与 GRSAI / 当前链路的关系

当前已接入的 GRSAI 更偏向单站点/单协议打通，不等于已经完成“多 Provider 通用接入框架”。

结论：

- GRSAI 链路可以继续保留，作为现有 Provider Adapter 的一个已跑通样本。
- 后续要支持更多服务商时，不能继续按“一个问题补一个临时分支”的方式扩展。
- 本次方案的目标正是把后续扩展升级为“结构化默认配置 + 宽松高级配置 + 专用 Adapter”的稳定框架。

## 推荐实施顺序

1. 先扩展模型元数据，加入结构化 `inputCapabilities` 与受控 `advancedConfig`。
2. 后台补视频模型能力开关和高级配置编辑入口。
3. 画布视频节点改为按能力动态渲染输入口。
4. 视频代理补 APIMart 异步 adapter，打通真实失败链路。
5. 再根据新模型接入情况决定是否继续抽象更多协议层。
