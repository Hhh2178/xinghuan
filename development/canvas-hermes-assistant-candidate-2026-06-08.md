# 无限画布项目专属 Hermes 助手候选方案备忘

日期：`2026-06-08`

状态：`候选方案 / 未批准实施`

## 1. 背景

当前无限画布 2.0 已具备：

- 统一后台 `/admin`
- Provider / 模型管理
- 任务队列与 Worker
- 灰度与生产双入口
- 基于外部 API 服务商的图像 / 文本 / 视频接入框架

在此基础上，后续可能引入一套 AI 助手能力，协助两类工作：

1. 前端画布中的创作辅助
2. 后台中的 Provider 接入、配置检查和状态审计辅助

本备忘仅用于保留方案思路，便于后续继续评估，不代表当前版本已立项或已进入开发排期。

## 2. 目标

希望中的助手不是通用聊天入口，而是面向本项目的受限副驾驶：

- 能理解无限画布项目的上下文
- 能协助整理 API 服务商接入和配置草案
- 能协助检查灰度状态、任务链路和模型目录
- 能在前端为用户提供创作建议
- 不能越权修改生产环境、密钥、核心站点逻辑或高风险系统配置

## 3. 当前倾向

当前讨论后的倾向方案是：

`复用 Hermes 作为底层内核，但为无限画布项目单独搭建一套隔离运行实例`

这意味着：

- 不直接复用当前服务器上正在承载其他职责的 Hermes 运行实例
- 不从零自研另一套完整智能体框架
- 继续利用 Hermes 已有的模型路由、工具编排、记忆与技能机制
- 但在无限画布项目侧建立独立的运行边界、权限边界和审计边界

## 4. 为什么不直接挂当前 Hermes 实例

如果把当前服务器里已经在运行的 Hermes 直接接入无限画布，虽然接入速度最快，但会带来这些问题：

- 记忆上下文容易串线
- 工具权限通常偏大，不利于后台安全收口
- 与现有个人/公司 Hermes 角色边界不清
- 日志和审计记录难以证明“该助手只做了项目允许的事”
- 后续想拆分前端创作助手和后台审计助手时，运行边界会变得混乱

因此，当前不建议让无限画布直接依附在现有 Hermes 运行实例上。

## 5. 候选拓扑

### 方案 A：直接接当前 Hermes 实例

优点：

- 接入最快
- 复用现有配置成本最低

缺点：

- 风险最高
- 权限、记忆、日志、角色容易混在一起
- 不适合作为长期产品能力

当前建议：`不采用`

### 方案 B：复用 Hermes 内核，单独建立项目专属实例

优点：

- 开发速度与隔离性平衡最好
- 能复用 Hermes 现有能力栈
- 能把无限画布助手的 memory / tools / env / logs / service 独立出来
- 后续可以继续拆成多个项目内角色

缺点：

- 需要额外维护一套项目专属 runtime
- 需要设计明确的工具白名单和审计链

当前建议：`优先评估`

### 方案 C：在无限画布项目中完全自建独立助手服务

优点：

- 边界最清楚
- 长期产品化自由度最高

缺点：

- 成本最高
- 需要重做 Hermes 已有的大量能力
- 当前阶段投入产出比偏低

当前建议：`暂不优先`

## 6. 两套助手的职责划分

### 6.1 前端创作助手

面向对象：

- 登录后的画布用户

主要职责：

- 根据当前节点、素材和目标生成创作建议
- 帮用户推荐工作流结构、节点组合、提示词和参数
- 解释模型差异、输入要求和常见失败原因
- 协助把自然语言需求整理成更明确的画布操作建议

权限边界：

- 默认只读当前用户的工作区上下文
- 不读取后台密钥
- 不修改 Provider 配置
- 不触发部署、重启、数据库写入或系统命令
- 不跨用户读取画布、素材和历史任务

### 6.2 后台审计 / 配置助手

面向对象：

- 管理员或开发者

主要职责：

- 协助梳理新 API 服务商的接入方案
- 生成 Provider / 模型配置草案
- 提示协议类型、参数 schema、能力分类和验收路径
- 辅助检查灰度状态、任务链路、模型目录和错误摘要
- 生成“建议变更”与“风险说明”，而不是直接接管生产

权限边界：

- 以只读检查和生成草案为主
- 可以读取有限的灰度状态、任务状态、模型目录和非密钥配置
- 不直接写入生产密钥
- 不直接修改正式环境路由、Nginx、systemd、数据库核心数据
- 高风险动作必须经过人工确认

## 7. 推荐的隔离方式

如果后续落地，推荐把无限画布助手建立为项目专属 Hermes runtime，至少做到以下隔离：

### 7.1 运行时隔离

- 独立 `Hermes home/profile`
- 独立 `config`
- 独立 `.env`
- 独立 `memory`
- 独立 `logs`
- 独立 systemd service
- 独立访问入口或内部 API token

### 7.2 工具白名单

默认只允许：

- 读取项目文档
- 读取模型目录与任务状态
- 读取灰度健康状态
- 生成配置草案
- 生成接入说明和验收清单

默认禁止：

- 生产部署
- 直接写生产密钥
- 删除数据
- 批量改配置
- 改 Nginx / systemd / 数据库结构
- 改内部代理服务

### 7.3 动作分级

建议把动作分成三类：

1. 只读动作
   - 可自动执行
2. 低风险建议动作
   - 可生成草案，由人确认后执行
3. 高风险动作
   - 只输出建议，不直接执行

## 8. 对 API 服务商接入的帮助方式

如果后续启用后台审计助手，它更适合承担这些工作：

- 识别新服务商更接近 `openai_compatible` 还是专用协议
- 给出现有框架下应复用的 `protocol`
- 生成模型导入建议
- 草拟 `parameterSchema`
- 草拟 `inputProfile`
- 给出灰度验收步骤
- 汇总接入风险与回滚点

它不应直接承担：

- 未审查即写入正式 Provider Key
- 未验证即推正式环境
- 在没有人工确认时改动高风险配置

## 9. 当前结论

当前最值得保留的结论是：

- “让无限画布拥有 AI 助手”是可行的
- 最合适的方向不是直接挂当前 Hermes 实例
- 更合适的是“复用 Hermes 内核 + 建立无限画布项目专属隔离实例”
- 助手应拆成“前端创作助手”和“后台审计 / 配置助手”两套能力面
- 后台助手应优先做“只读检查 + 配置草案 + 灰度验收建议”，而不是直接接管生产

## 10. 后续待判断事项

本方案后续若继续评估，需要再明确：

1. 采用单实例双角色，还是双实例分权
2. 助手入口是走画布内嵌面板、后台侧栏，还是独立管理页
3. 后台助手可读取哪些表、接口和日志摘要
4. 哪些动作属于“可自动执行”，哪些必须人工确认
5. 是否要让灰度环境提供专门的受限执行沙箱
6. 是否要把服务商接入流程进一步产品化为“协议适配模板 + 验收工作流”

在以上问题未定前，本文件只作为设计备忘，不作为实施承诺。
